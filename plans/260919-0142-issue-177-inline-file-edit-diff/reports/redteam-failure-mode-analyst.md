## Finding 1: Summary-time differ has no upstream memoization and is invoked from three independent, unmemoized full-history scans; the shared 64-entry cache will thrash for any real session

- **Severity:** Critical
- **Location:** Phase 1, section "Decisions" #2 and #11 (`diffHunks`/`createDiffHunks`); Phase 1 §"tool-presentation.ts" (`toolPresentation()` `file` case); plan.md "Compatibility, rollout, and rollback" performance claim
- **Flaw:** The plan's entire performance argument for running `structuredPatch` inside the 3-second/summary polling path rests on decision 2: "the result is memoized on the pair so `toolBodyPresentation()` reuses it for free" and on decision 11's "bounded and testable" `DIFF_MEMO_ENTRIES = 64` cap. But `toolPresentation()` (which the plan wires the new `diffHunks()` call into) is called from **three separate production call sites**, each of which rebuilds the *entire* node history from scratch on *every render*, with no `useMemo` gate and a timestamp (`Date.now()`) baked into the memo key surface:
  - `packages/web/src/components/workflows/NodeTranscriptPane.tsx:262-270` — `buildAgentHistory({ rows: visibleMessages, events, nodeId: row.nodeId, nowMs })` computed directly in the render body (no `useMemo`), and its own internal poll loop re-triggers via `setTimeout(..., 1000)` (1-second cadence, not 3) at `NodeTranscriptPane.tsx:203-206`.
  - `packages/web/src/experiments/console/components/inspect/ConsoleExecutionHistory.tsx:204-211` — identical unmemoized pattern, identical 1000 ms drain loop.
  - `packages/web/src/experiments/console/components/ConsoleNodeRoom.tsx:650` — a third independent call site for the same underlying node.
  Each of these iterates **all** rows returned by `drainNodeMessages` (`packages/web/src/lib/node-message-pages.ts`), which accumulates the full, unbounded per-node history (paged in 100-row chunks, never windowed/truncated) — not just newly arrived rows. `toToolItem()` (`packages/web/src/lib/agent-history.ts:169-199`) calls `toolRowPresentation()` → `toolPresentation()` for **every** row, every time, regardless of whether the row's content changed since the last render.
- **Failure scenario:** A realistic coding-agent session (the kind Archon exists to run) easily produces well over 64 distinct `Edit` calls in one node's history. Once the number of *distinct* before/after pairs seen across a single `buildAgentHistory` pass exceeds `DIFF_MEMO_ENTRIES = 64`, the shared, module-level `diffHunks` `Map` (one instance for the whole app, per Phase 1's `export const diffHunks: DiffHunksFn`) evicts and reinstates entries within the *same* pass — row 65's insertion evicts row 1's entry, so the next second's identical full re-scan misses on row 1 again. The result is that `structuredPatch` (not a cache hit) runs on the majority of file rows **every ~1 second while the run is live**, for as long as the transcript stays open. This is not a bounded, "cheap because memoized" cost as decision 2 claims — it is an unbounded, recurring full re-diff proportional to `min(distinct pairs, total rows)` on every poll tick, directly contradicting the story's own precedent constraint (Story 1.3's ban on expensive summary-time work) that decision 2 explicitly invokes to justify this design.
  Additionally, Console can mount the execution-history view *and* the node room for the same node concurrently (Phase 2 itself: "the Console mounts the history list in more than one place"), so the same node's rows get scanned and diffed by two or three independent unmemoized passes competing for the same 64-slot cache, further accelerating eviction.
- **Evidence:**
  - `packages/web/src/components/workflows/NodeTranscriptPane.tsx:262-270`: `const agentHistory: AgentHistory = row === null ? {...} : buildAgentHistory({ rows: visibleMessages, events, nodeId: row.nodeId, nowMs });` — no `useMemo`.
  - `packages/web/src/components/workflows/NodeTranscriptPane.tsx:203-206`: `timer = setTimeout(() => { void runDrain(beginNodeMessageRefresh(next)); }, 1000);`
  - `packages/web/src/experiments/console/components/inspect/ConsoleExecutionHistory.tsx:204-211`: identical pattern (`nowMs = Date.now(); const { items } = buildAgentHistory({...})`).
  - `packages/web/src/experiments/console/components/ConsoleNodeRoom.tsx:650`: third call site.
  - `packages/web/src/lib/node-message-pages.ts:202`: `limit: 100` is a *page* size for draining, not a cap on total accumulated rows.
  - Phase 1 contract: `export const DIFF_MEMO_ENTRIES = 64;` (phase-01-start.md:58), single shared instance (`export const diffHunks: DiffHunksFn`, phase-01-start.md:74).
- **Suggested fix:** Wrap `buildAgentHistory` (or at minimum the tool-row presentation loop) in a real memoization keyed on stable row identity/content, not `Date.now()`; size `DIFF_MEMO_ENTRIES` relative to a realistic transcript (or key the cache per node/room rather than globally); and/or move the diff computation out of the per-poll summary path entirely into the already-lazy body resolver, computing it only when a row is opened (contradicting decision 2's premise, but avoiding the thrash).

## Finding 2: Phase 2's "Contrast check" cannot be faithfully executed under `bun test` + happy-dom as specified

- **Severity:** Critical
- **Location:** Phase 2, section "Tests first" → "Contrast check (recorded, not snapshot)"; Phase 2 exit criteria ("Marker and line colors measured ≥ 4.5:1 on both themes (or the documented fallback applied)")
- **Flaw:** The plan instructs: "resolve the computed colors of a `−` marker over the delete-tinted cell and a `+` marker over the insert-tinted cell using the same `color-mix` strings the CSS uses, and assert ≥ 4.5:1 with the contrast helper the visual e2e already uses (port the small helper if it is e2e-only)." The only existing implementation of that helper, `resolveColorIn` in `e2e/ui/agent-tool-row-visual.spec.ts:528-545`, is fundamentally not portable: it is `async`, takes a Playwright `Locator`, calls `room.evaluate(...)` to run code **inside a real Chromium tab**, sets `probe.style.color = colorCss`, reads `getComputedStyle(probe).color` (which requires the browser's real CSS engine to resolve `color-mix(in oklch, ...)`), and then rasterizes that resolved color through a **`<canvas>` 2D context** (`doc.createElement('canvas').getContext('2d')` + `getImageData`) to get concrete RGBA bytes. None of this is available under `bun test` + happy-dom: happy-dom does not implement CSS Color Module 5 `color-mix()`/`oklch()` resolution in its `getComputedStyle`, and its `HTMLCanvasElement.getContext('2d')` is not a real rasterizer (no native canvas backend is wired into this test environment). If the helper is ported unmodified, `ctx` will be `null` (or unable to draw), and the code's own fallback (`if (ctx === null) return { resolved, c: { r: 0, g: 0, b: 0, a: 0 } }`) silently returns transparent black for both foreground and background — the two colors under test are indistinguishable from garbage rather than from a real measurement.
- **Failure scenario:** An engineer implementing Phase 2 either (a) discovers `resolveColorIn` doesn't run under happy-dom and burns time trying to make canvas/`color-mix` work in a DOM simulator that was never built for it, or (b) ports it literally, gets `contrastRatio(black, black) = 1` for both markers (since fg.a=0 collapses the composite to the background color, giving identical fg/bg luminance), and the test fails outright with a number that says nothing about the real rendered contrast — masking whichever theme actually has the accessibility problem the check exists to catch. Either way, the phase-2 exit criterion as scoped for a *component/unit* test is not achievable by "porting" the existing helper; it requires a fundamentally different implementation (e.g., hardcoding each theme's resolved RGB token values and doing the `color-mix` math in pure JS), which the plan never specifies.
- **Evidence:**
  - `e2e/ui/agent-tool-row-visual.spec.ts:528-545` (`resolveColorIn`, Playwright `Locator.evaluate` + `getContext('2d')` + `getImageData`).
  - `e2e/ui/agent-tool-row-visual.spec.ts:591-598` (`contrastRatio`, the only pure-JS piece — everything upstream of it in the existing helper is browser-bound).
  - No pre-existing non-e2e contrast helper exists in `packages/web/src` (`grep -rln "contrastRatio\|luminance" packages/web/src` returns nothing).
  - Phase 2 exit criteria list this as a must-pass gate before Phase 2 is considered done, and Phase 3 only re-measures numbers, it does not re-derive the mechanism.
- **Suggested fix:** Either drop the component-level contrast assertion and rely solely on the Phase 3 Playwright measurement (which does run in a real browser and can legitimately reuse `resolveColorIn`), or replace the Phase 2 "port the helper" instruction with an explicit pure-JS contrast calculation against hardcoded token values, documented as *not* verifying the actual rendered `color-mix()` output.

## Finding 3: Decision 2's compliance argument ("reuses it for free") depends on a cache-survival guarantee the design does not actually provide

- **Severity:** High
- **Location:** Phase 1, "Decisions" #2 ("The diff is the one sanctioned summary-time computation")
- **Flaw:** Decision 2 argues this feature does not violate Story 1.3's prohibition on expensive summary-time computation because "the result is memoized on the pair so `toolBodyPresentation()` reuses it for free," and because "A test proves repeated `toolPresentation` calls on one Edit row invoke the differ once." That test (Phase 1, `tool-presentation.test.ts` bullet "Memo reuse across summary and body") only proves reuse **in isolation**, calling `toolBodyPresentation` twice back-to-back with nothing else touching the shared cache in between. It does not — and, given the architecture, cannot — prove reuse under the realistic condition where dozens of *other* rows' summary passes are interleaved between the first and second call, which is exactly what happens once Finding 1's three unmemoized call sites are polling live. The plan treats "memoized" as a blanket safety property, but the memo is a bounded LRU shared across the whole app; its hit rate depends entirely on working-set size, which the plan never bounds or tests against a realistic transcript size.
- **Failure scenario:** In the exact scenario this feature is built for — a long file-editing session — the "summary-time computation is fine because it's cached" justification silently stops being true, and the plan has no test that would catch the regression (all differ tests use small, isolated fixtures or a `memoEntries: 2` instance explicitly built to demonstrate eviction as a *feature*, never to prove the production 64-entry instance survives a realistic multi-row poll cycle).
- **Evidence:** Phase 1 contract's own eviction test row ("determinism and memo identity ... a third distinct pair on a `memoEntries: 2` instance evicts the first") *proves eviction is real and expected behavior of this exact mechanism* — the plan demonstrates the failure mode in its own test suite without connecting it to the production call pattern documented in Finding 1.
- **Suggested fix:** Add an explicit acceptance test/benchmark that runs `buildAgentHistory` (or a stand-in loop over `toolPresentation`) across >64 distinct file-edit pairs in one pass and asserts the total number of `structuredPatch` invocations stays bounded — or revise decision 2's text to acknowledge the cache is best-effort, not a compliance guarantee.

## Finding 4: New DOM-rendering library added, for the first time, to two already-large interaction-test files with no timing budget considered, in a repo that has previously shipped exactly this class of `bun test` timeout regression

- **Severity:** Medium
- **Location:** Phase 2, section "Tests first" → "Legacy interaction — `LegacyNodeRoom.test.tsx`" and "Console — `ConsoleNodeRoom.test.tsx` and `ConsoleExecutionHistory.test.tsx`"
- **Flaw:** `LegacyNodeRoom.test.tsx` (2065 lines) and `NodeRoom.test.tsx` (1856 lines) currently never import `react-diff-view` or mount a real `<table>`-based diff component; that import is currently confined to `virtualized-diff.tsx`/`file-viewer.test.tsx`, which is exercised only via `renderToStaticMarkup` (server rendering, no live DOM). Phase 2 adds real `Diff`/`Hunk`/`Decoration` mounting through `createRoot` inside the manually-wired happy-dom `Window` instance that `LegacyNodeRoom.test.tsx` installs once at module load (`installHappyDom()` at `LegacyNodeRoom.test.tsx:246-283`), for interaction tests (open row → toggle Raw → close Raw) across multiple fixtures (both-sides, failed, multi-hunk, identical, one-sided, no-input) per surface. AGENTS.md's own documented CI history (`#2473`, `#2240`, `#2306`) shows this exact repo has repeatedly been bitten by underestimating per-test cost against Bun's 5000 ms default timeout, specifically flagging that a "gradient" cost profile (genuine, uncounted work) is the diagnostic sign to watch for — and the plan adds a real reconciliation-heavy table component to the interaction suite without establishing any baseline or acknowledging the risk class at all.
- **Failure scenario:** Bun's per-test default timeout (5000 ms) is shared infrastructure; if any one of the new diff-mounting interaction tests (which now perform real DOM diffing/reconciliation for a `Diff` table, not just plain text nodes) pushes near that bound on a loaded CI runner, the failure will present as an intermittent, hard-to-attribute timeout exactly matching the pattern AGENTS.md warns about — and because the plan does not call for measuring test durations before/after, there's no signal to distinguish "normal variance" from "this specific change made the suite meaningfully slower."
- **Evidence:** `wc -l packages/web/src/components/workflows/{LegacyNodeRoom.test.tsx,NodeRoom.test.tsx}` → 2065 / 1856 lines; `LegacyNodeRoom.test.tsx:246-283` (`installHappyDom`, module-scope, not per-test); AGENTS.md "Testing" section, `#2473`/`#2240`/`#2306` guidance on gradient-vs-bimodal timeout diagnosis.
- **Suggested fix:** Capture `--reporter=junit` timings for the touched test files before and after Phase 2 lands, per AGENTS.md's own prescribed methodology, and flag if any new test case's duration trends toward the 5000 ms budget.

## Finding 5: `content`/`new_content` false-positive family inference now drives a visually authoritative diff UI, not just a mislabel

- **Severity:** Medium
- **Location:** Phase 1, "Risks and safeguards" (`A content/new_content pair also matches a payload that happens to carry both keys...documented, not special-cased`); `packages/web/src/lib/tool-presentation.ts:142-146` (`BEFORE_AFTER_PAIRS`)
- **Flaw:** `inferFamily()` already treats any row carrying **both** top-level `content` and `new_content` keys as `family: 'file'` regardless of the tool's actual semantics (`packages/web/src/lib/tool-presentation.ts:468-470`). Before this plan, misclassification here only affected a generic body renderer (path + preview) — a mild, low-consequence bug. After this plan, the same misclassification now renders a full syntax-colored diff table with `+n`/`−n` badges and insert/delete-tinted lines: a much stronger, more misleading visual claim ("this tool changed a file") about a tool that may have nothing to do with file editing. The plan explicitly acknowledges the false-positive is possible and accepts it as "documented, not special-cased," but the test plan only covers this pairing under the `file`-family test block in `tool-presentation.test.ts` — there is no test anywhere in the three phases that exercises a *non-file* tool (e.g. a hypothetical memory/note/message tool using `content`/`new_content` for unrelated fields) to confirm the diff UI's blast radius is actually bounded to genuine file edits in practice.
- **Failure scenario:** A future or third-party tool (MCP server, community provider) that happens to use `content`/`new_content` as field names for a non-file operation (e.g., updating a note, a memory entry, a config blob) will silently render as an "inline file diff" with the full visual weight of a code change, with no test in this plan's suite to catch or even document the concrete shape of that failure beyond a one-line risk note.
- **Evidence:** `packages/web/src/lib/tool-presentation.ts:142-146` (`BEFORE_AFTER_PAIRS` includes `['content', 'new_content']`); `packages/web/src/lib/tool-presentation.ts:468-470` (`inferFamily` loop returns `'file'` on any matching pair with no name/shape gate); plan.md Phase 1 risk note accepting this without a mitigating test.
- **Suggested fix:** At minimum, add a negative test asserting a non-file-aliased tool name with a `content`/`new_content` pair still renders as a diff today (to make the accepted behavior explicit and regression-proof) rather than leaving it purely as prose in the risk section.
