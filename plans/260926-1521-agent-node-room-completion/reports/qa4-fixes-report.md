## Findings and fixes

### VQ4-1 (major) — redirect reply drawn above the redirect

**Fix, provider side**: DeepSeek (`community/deepseek/event-bridge.ts`) and Grok ACP (`grok/acp-event-bridge.ts`) each mint their thinking/assistant block ids from a per-instance counter that restarts at 1 every turn, because the state object (`DeepseekEventState`/`GrokAcpEventState`) is constructed fresh inside `driveDeepseekAcpTurn`/`driveGrokAcpTurn` — one call per turn, confirmed by reading both call sites. A redirected turn's first block therefore minted the exact id an earlier turn already used. Both now carry a `turnId` (defaults to `randomUUID()`, injectable for deterministic tests) baked into every block id (`deepseek-<turnId>-thinking-1`, `grok-acp-<turnId>-assistant-2`). `grok/event-parser.ts` (the `--single` transport's `GrokEventParser`) got the identical treatment for consistency, even though a `--single` run is always one turn today, so it carries no live collision.

**Fix, web side**: `packages/web/src/lib/project-text-transcript.ts` kept a `Map<key, openRow>` that a keyed delta/snapshot could reopen from anywhere in the transcript, with no adjacency requirement — so a turn-2 delta whose key happened to collide with a turn-1 key (exactly the provider bug above, but also true of any already-persisted transcript recorded before the provider fix) found and appended to the stale row instead of opening a new one after the rows in between. Replaced the map with a single "current open row" tracked by exact key match: any row that isn't a continuation of that exact key — a different block, a non-text row, or a `complete`-mode row — closes it, and a later delta/snapshot that reuses the same key opens a fresh row rather than reviving the closed one. This is what repairs the two already-broken persisted runs below without touching their stored data.

**Verified — unit**: `event-bridge.test.ts` (DeepSeek, Grok ACP) and `event-parser.test.ts` each gained a case proving two turns mint different block ids for the same kind/sequence; `project-text-transcript.test.ts` gained the adjacent-vs-non-adjacent snapshot cases and a direct regression case (a delta reusing an earlier block id after an intervening tool+operator row starts a fresh row). One pre-existing test (`replaces snapshots only inside the matching stream`) asserted the old cross-row-reopen behavior as the bug fix now forbids it — renamed and reworked into two cases (adjacent reopen still replaces; non-adjacent reopen starts fresh) rather than deleted.

**Verified — real app, already-persisted data**: reloading the round-4 DB's own `eb24d7ff…`/`d9722269…` runs through this build shows the reply correctly rendered **after** the operator row in both shells, with no fused/duplicated text — `pair-console-deepseek-redirect-fixed.png`, `pair-legacy-deepseek-redirect-fixed.png`, `pair-console-grok-redirect-fixed.png`, `pair-legacy-grok-redirect-fixed.png` (paired against mockup `s4`). **Verified — real app, fresh runs**: dispatched fresh `vq4-deepseek` (run `d6209225…`) and `vq4-grok` (run `6bc829dc…`) turns, stopped mid-tool, sent a typed redirect, and confirmed via the raw message API that turn 1 and turn 2 now carry **different** turn-id segments in their block ids (`deepseek-43c0ddb7-…-thinking-1` vs `deepseek-c6d52edb-…-assistant-1`; `grok-acp-5c5b1e9a-…` vs `grok-acp-d3b261a0-…`) — the provider-side fix confirmed live, not just in the unit test. ### VQ4-6 (minor) — durable queue vanishes during the abandon window

**Fix, web (dock visibility)**: `steeringDockMode` in `steering-dock.ts` only entered the read-only `'finished'` mode when `nodeTerminal === true`; a run that went non-live via Cancel/Abandon, but whose node hadn't yet posted its own terminal event, fell straight through to `if (!input.live) return 'hidden'`, hiding the band (and the queued item inside it) for the whole window. Widened the guard to `(nodeTerminal === true || !input.live)`: a non-live run qualifies for the same read-only treatment a terminal node gets, because sending is impossible either way — an abandoned run's still-queued item is exactly as undeliverable as a proven `never_sent` row. `ComposerDock.tsx`/`ConsoleComposerDock.tsx`'s one-shot queue-hydration effect had the identical `if (!nodeTerminal) return` gate (so even with the mode fix, a cold-opened room during this window would never fetch the queue to populate it) — widened the same way.

One pre-existing test (`hidden and detached modes never read`) asserted the old behavior (`live: false` alone never reads) as intentional; it directly encoded the bug this fix corrects, so it was renamed and reworked (a non-live, non-terminal row now does one read, settling to `hidden` when genuinely empty; the detached-mode "never reads" half is untouched and still passes).

**Verified — unit**: `steering-dock.test.ts`'s existing "finished requires explicit node-terminal evidence" describe block gained the non-live-alone case (now `'finished'`, was `'hidden'`) with a comment explaining why, and the empty-queue control case. `ComposerDock.test.tsx`/`ConsoleComposerDock.test.tsx` gained an end-to-end case: `live: false, nodeTerminal: false`, one `queued` row from the server — the band renders read-only with no textarea/Stop/Queue/Send now controls.

**Verified — real app**: dispatched a fresh `vq4-omp` run, waited for the client to confirm the queued item on screen (removing test-harness poll-latency noise from the measurement), then called Abandon. ## Concerns

**VQ4-6, executor half — not changed.** The coordinator asked me to check whether the executor can notice cancellation sooner during a running tool, and improve if safe. I traced it: the mid-stream cancel check (`dag-executor.ts:2681`, `shouldContinueStreamingForStatus`) lives **inside** the `for await (const msg of stream)` loop body, so it only runs when a new provider chunk arrives; a silent long-running tool (no interleaved chunks) yields none, so Abandon's effect is bounded by however long the current tool call takes to finish naturally, not by the 10s `CANCEL_CHECK_INTERVAL_MS` throttle — the throttle is a red herring for this specific gap. The fast path that **does** interrupt mid-tool immediately (`interruptibleHandle`, registered around `dag-executor.ts:2590`) is what operator-triggered Stop uses; `abandonWorkflow` (`packages/core/src/operations/workflow-operations.ts:447`) is deliberately a pure DB write with no in-process signal, so it works uniformly across every calling surface (CLI, web, chat, Slack) regardless of which process is actually running the DAG executor. Building a cross-process cancellation signal is a real architectural change, not a bounded fix, and I judged it outside "improve if safe." The precedent a future fix would copy already exists in the same file: the idle-await path (`dag-executor.ts:540-565`) already runs a `setTimeout(tick, CANCEL_CHECK_INTERVAL_MS)` timer **decoupled** from the stream loop — the same pattern applied to the streaming cancel check would close this gap without touching the loop body's own logic. I did not make this change.

**VQ4-6, mockup contradiction reused on purpose.** During the abandon window the header honestly still reads `Running`/`running…` (the node's own event hasn't landed) directly above a queue band that already reads `node finished · none of this was sent` once the node does fail. The coordinator's instruction was explicit — reuse the existing `'finished'` contract state rather than invent a new "cancelling" disclosure — so this is not a fix I made or a gap I'm flagging as new; it's the deliberate, minimal scope the coordinator chose, listed here only so it's visible alongside the executor-latency root cause rather than silently accepted.
