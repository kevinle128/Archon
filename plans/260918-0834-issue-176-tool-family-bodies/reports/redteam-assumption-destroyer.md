## Finding 1: The plan's core sequencing claim ("Story 1.2 is in flight") is false at review time — the dependency it treats as near-certain does not exist

- **Severity:** Critical
- **Location:** `plan.md`, "Evidence and authority" bullet ("Story 1.2 (#175) is `status:processing` with an `ak-implement` run in flight") and "Resolved source conflicts" ("Sequencing with Story 1.2. This plan assumes 1.2's landed structure.")

None of that is true in this checkout.
- **Failure scenario:** Phase 2 begins, the scout pass looks for the 1.2 slot in `NodeRoom.tsx`/`ConsoleAgentHistoryList.tsx`, and finds the **original Story 1.1 bridge still in place** (`Input`/`Output` nested `<details>` calling `formatToolIo()`), not the Raw-toggle slot the whole phase is architected around. Phase 2's own "Pre-execution gate" ("If not [merged], stop and coordinate") is the only thing standing between this plan and building against a structure that doesn't exist — but the plan's narrative sections (goal, end-to-end design, evidence) all assert the dependency is essentially satisfied, which will mislead whoever executes Phase 1 (which shares files with 1.2, per its own "Coordinates with Story 1.2" note) into believing the merge is close, when in fact issue #175 has no branch, no PR, and no code at all.
- **Evidence:**
  - `_bmad-output/implementation-artifacts/agent-node-room/sprint-status.yaml:60`: `1-2-inspect-the-raw-payload-of-a-tool-call: backlog` (not `in-progress`, not `review`).
  - `packages/web/src/components/workflows/NodeRoom.tsx:13,440,448`: `formatToolIo` is still imported and used inside the Input/Output bridge — the exact "temporary bridge" that Story 1.2's own plan says it removes.   - Story 1.2's own plan (`plans/260918-1038-issue-175-raw-payload-toggle/plan.md:45`) independently records: "Issue #175 is open with no PR, no branch, and no worktree."

## Finding 2: The grep `output_mode` default contradicts the plan's own cited authority, reintroducing the exact bug that authority document exists to prevent

- **Severity:** Critical
- **Location:** `plan.md`, "Resolved source conflicts" → "Grep arm precedence"; `phase-01-start.md`, rule table row for `search`
- **Flaw:** The plan states as a resolved fact: "**Grep arm precedence:** `input.output_mode` → the captured Claude output `mode` field → `matches`" — i.e., when `output_mode` is absent, default to the `matches` (content) arm. But the plan's own primary source, `tool-presentation-contract.md:122-133`, explicitly documents the opposite for Claude: `GrepInput.output_mode` **defaults to `files_with_matches`** (the `paths` arm), and states this exact point is why the design exists: _"Choosing the arm from the family alone would mis-parse the majority of Claude's grep calls."_ The contract's "absent → treated as content" rule is scoped explicitly to **OMP's grep only** ("A provider that sends no `output_mode` at all (**OMP's `grep`**)..."), not to Claude.
- **Failure scenario:** A real Claude `Grep` call that omits `output_mode` in its persisted input (the schema-documented default case) returns bare file paths as its output. Under the plan's rule, this row's body arm defaults to `matches`, so the body renderer tries to regex-parse plain filenames as `path:line:text` and fails to match, degrading to `{path:null,line:null,text}` items shown inside a "matches" box — exactly the "majority of Claude's grep calls" mis-parse scenario `SPEC.md:100` was written to prevent, just reached through the "absent" branch instead of the "family alone" branch the authors already fixed.
- **Evidence:**
  - `_bmad-output/specs/spec-agent-node-room/tool-presentation-contract.md:124`: "`GrepInput.output_mode` is `"content" | "files_with_matches" | "count"` and **defaults to `files_with_matches`**."
  - `_bmad-output/specs/spec-agent-node-room/tool-presentation-contract.md:133`: "A provider that sends no `output_mode` at all (OMP's `grep`) is treated as `content`" — scoped to OMP.
  - `_bmad-output/specs/spec-agent-node-room/sources/spec-readable-agent-transcript/SPEC.md:100`: "`GrepInput.output_mode` defaults to `files_with_matches`, so Claude's grep returns **file paths, not `path:line` matches**, by default — the body arm must be chosen from `output_mode`, not from the family."
  - `_bmad-output/specs/spec-agent-node-room/test-plan.md:20` itself conflicts with the contract too ("absent → `matches`" with no provider qualifier) — a source contradiction the 176 plan silently picks a side on without ever naming the conflict, despite having a whole "Resolved source conflicts" section built for exactly this purpose.
  - `plans/260918-0834-issue-176-tool-family-bodies/plan.md:57` and `phase-01-start.md` search-arm row both encode "absent → matches" as settled.
- **Suggested fix:** Add this as a named entry in "Resolved source conflicts," resolve it against `tool-presentation-contract.md`/`SPEC.md` (the higher-authority tier-2 source per the plan's own precedence order), and make the default for **Claude specifically** `paths` (files_with_matches), reserving `matches`-on-absent for providers (OMP) that are confirmed to return content by default. Phase 1's capture step must explicitly test the "default/absent `output_mode`" case for Claude and check it against `paths`, not assume `matches`.

## Finding 3: The web body's markdown reuses a pipeline that renders live, clickable links — contradicting the plan's own stated security guarantee

- **Severity:** High
- **Location:** Phase 2, "Security considerations" ("The web arm's URL is rendered as text, not as an anchor, so stored data cannot become a click target.")
- **Flaw:** The stated mitigation only covers the tool's own top-level `url` field. But the `web` body's `markdown` field (per Phase 1's architecture, "`markdown` = normalized text") is fed through "the existing `ReactMarkdown` + `rehypeHighlight` pipeline" per Phase 2's architecture note — the **same** pipeline instance whose `MARKDOWN_COMPONENTS.a` override renders real `<a target="_blank" rel="noopener noreferrer">` elements for any `[text](url)` markdown link. `body.markdown` is untrusted third-party content: the output of a `WebFetch`/`WebSearch` tool call, i.e., whatever the fetched page or search result contained, which the agent has no control over and which can be adversarial (prompt-injection-style content deliberately crafted to look like a legitimate citation link).
- **Failure scenario:** An operator expands a `WebFetch` row whose fetched page contains `[Click here to verify your session](https://attacker.example/phish)`. The plan's markdown pipeline renders this as a real, clickable, new-tab-opening anchor inside the tool body — directly contradicting the plan's stated "no navigation from stored data" guarantee, which the plan believed it had achieved by only text-ifying the row's own `url` field.
- **Evidence:**
  - `packages/web/src/components/workflows/NodeRoom.tsx:84-91` (`MARKDOWN_COMPONENTS.a`): renders a live `<a>` with `target="_blank" rel="noopener noreferrer"` for any markdown link, reused unmodified per Phase 2.
  - `phase-02-two-surface-renderers.md`, Requirements: "Web: URL header (plain text, not a link — no navigation from stored data), title beneath when present, **markdown body through the existing pipeline**" — the same sentence that claims no navigation is possible also routes the body through the link-rendering pipeline.
  - `phase-01-start.md` rule table row 9/architecture: `web` body's `markdown` = normalized output text, sourced from `result`/tolerant-tail fields of `WebFetch`/`WebSearch` output — i.e., third-party fetched content, not agent-authored text.
- **Suggested fix:** Either strip/neutralize link and image nodes specifically for the `web` body's markdown rendering (a distinct `rehype`/`remark` component override disabling `a`/`img` for this one body kind), or explicitly document and get sign-off on the residual risk — the plan currently asserts the risk is closed when it is not.

## Finding 4: The audit's own headline pass rate (1.02%) is not proven to match the denominator rule the plan later commits to implementing

- **Severity:** High
- **Location:** `plan.md`, "Verified repository facts" (the 1,966-call-row / 20-generic / 1.02% claim) vs. `phase-03-audit-gate-and-verification.md`, Requirements ("Denominator = one row per tool call: `metadata.tool_phase === 'call'`, **or no `tool_phase` and no `payload.output`**")
- **Flaw:** `plan.md` reports the corpus measurement as "3,794 tool rows, 1,966 call rows" and "20 resolve to generic — 1.02%, under the 2% gate," presented as evidence the design will clear the release gate. But it never states which of the two denominator rules produced "1,966" — in particular, whether any rows without `tool_phase` metadata were included via the fallback clause the script is required to implement. If the fallback clause pulls in additional rows (e.g., legacy or malformed transcript rows) that plan.md's manual count did not include, the actual `--check` run against the same corpus can produce a different fraction than the one the plan cites as proof of safety margin.
- **Failure scenario:** Phase 3 implements the script per its own denominator spec, runs it against the same corpus described in `plan.md`, and gets a fraction different from 1.02% because rows without `tool_phase` (of unknown count and unknown family distribution) are now included. If that pulls the number above 2%, the "Success criteria" checkbox ("audit record exists ... `--check` gate passes on the recorded corpus") fails on the very first real run, despite `plan.md` treating 1.02% as an established, low-risk fact throughout the rest of the document (e.g., Phase 1's own success criterion: "Replaying the local corpus with `output: undefined` still yields 20/1,966 generic").
- **Evidence:**
  - `plan.md`, "Verified repository facts": "Measured on the local deployment corpus... 3,794 tool rows, 1,966 call rows... 20 resolve to `generic` — 1.02%" — no mention of the `tool_phase`-missing fallback anywhere in this measurement paragraph.
  - `phase-03-audit-gate-and-verification.md`, Requirements: "Denominator = one row per tool **call**: `metadata.tool_phase === 'call'`, or no `tool_phase` and no `payload.output`." This second disjunct is absent from the plan.md measurement methodology.
  - `packages/workflows/src/dag-executor.ts:2426-2432`: confirms `tool_phase: 'call'` is written on every tool-call transcript row by the current code path — meaning the fallback clause exists to catch rows this code path did _not_ produce (a different/older writer), whose shape and count are unverified by the cited 1.02% number.
- **Suggested fix:** Re-run (or explicitly state how) the 1,966/20 measurement was derived, using the exact denominator rule Phase 3 will implement, before citing it as evidence in `plan.md`. If the fallback clause is meant for a currently-empty class of rows, say so explicitly and verify the count is actually zero in the corpus quoted.

## Finding 5: "The deployment database" is not a coherent concept for a single-tenant-per-install product, but the release gate is built as if it were

- **Severity:** Medium
- **Location:** `phase-03-audit-gate-and-verification.md`, Requirements ("`--db <path>` defaults to `${ARCHON_HOME ?? ~/.archon}/archon.db`") and `.claude/skills/release/SKILL.md` step addition ("re-run the audit against the deployment database first")
- **Flaw:** Per `AGENTS.md`'s "Single-Tenant per Install" principle, there is no single canonical "the deployment database" — every install (including whichever machine happens to run `/release`) has its own local corpus shaped by that operator's own usage. The plan commits one snapshot (`docs/release-audits/generic-fallback.json`, sourced from one contributor's personal `~/.archon/archon.db` on 2026-09-18) into the shared repository as the basis for a release gate that will be reused by anyone who runs `/release` from `dev`, on whatever machine they happen to be using.
- **Failure scenario:** A different maintainer runs `/release` from a machine with an empty or differently-shaped `~/.archon/archon.db` (e.g., CI, or a fresh laptop). The gate either passes trivially against a near-empty/unrepresentative corpus (false confidence — the real production corpus that matters was never measured), or the instruction "re-run the audit against the deployment database first" has no well-defined target to point at, since "the deployment" is whichever single install happens to be running the release, not a fixed system-of-record.
- **Evidence:** `AGENTS.md`, "Single-Tenant per Install": "One isolated instance per operator or client... Keep the data model and runtime single-tenant: no per-tenant isolation, row-scoping, or tenant multiplexing." `plan.md`'s own corpus evidence is explicitly sourced from `/Users/agent/.archon/archon.db`, a single local instance, not any distinguished "production" system the release process has access to.
- **Suggested fix:** Either scope the audit explicitly as "the release author's own local corpus, refreshed at release time" (drop the word "deployment," which implies a canonical shared system), or define which specific install's database is authoritative for gating OSS releases of this project, and document that decision alongside the recorded JSON.

## Finding 6: The "output never reclassifies family" invariant is real, but the plan's `body.kind: 'generic'` reuse across `search`'s count arm and the `generic` family blurs the one signal the audit depends on

- **Severity:** Medium
- **Location:** `phase-01-start.md`, architecture table (`search` row: "`count` → `generic` with the count as a badge")
- **Flaw:** The corpus audit (Phase 3) and Phase 1's own audit-invariant test both key off `ToolPresentation.family === 'generic'`, and the plan is correct that resolving a `search` row's **body** to the `generic` `ToolBody` kind does not touch `family` (which stays `'search'`). That distinction is correct in the code as traced, but the plan never states it explicitly anywhere reviewable — the phrase "`count` → `generic`" appears identically in both `plan.md` and `phase-01-start.md` without disambiguating "body kind `generic`" from "family `generic`," in a document whose entire audit-gate mechanism hinges on that exact distinction never being confused by whoever writes the count-arm code.
- **Failure scenario:** An implementer reads "count → generic" and, seeing the same word used for the family-resolution fallback everywhere else in the same document, sets `family: 'generic'` for count-mode search rows (a natural misreading, since every other "generic" in the plan means the family). This silently inflates the generic-fallback numerator for a family (`search`) that should never contribute to it, and could just as easily flip the audit result across the 2% line in either direction without any test catching it, since Phase 1's own audit-invariant test only checks that _swapping output for undefined_ doesn't change family — it does not check that resolving the count arm specifically leaves `family` untouched under a defined output.
- **Evidence:** `phase-01-start.md` architecture table, `ToolBody` union: `{ kind: 'generic'; fields: ...}` is the same `kind` literal reused for the `todo`/`task`/`generic`-family fallback body **and** the search count arm; `plan.md`'s Phase 1 requirement list only asserts "family resolution stays name-plus-input only; output never reclassifies a family (audit invariant)" without a corresponding requirement pinning `family` to `'search'` specifically when the body degrades to the generic kv shape.
- **Suggested fix:** Add an explicit unit test asserting `toolPresentation({name: <grep-like>, input: {pattern, output_mode: 'count'}, output: <n>}).family === 'search'` (not `'generic'`), and rename one of the two overloaded "generic" meanings in the plan text (e.g., call the search count body arm `count` rather than reusing the `generic` `ToolBody.kind`) to remove the ambiguity from the document itself.
