- (direction) Create Durable Workflow Runtime as an independent feature; do not modify Agent Node Room SPEC, epics, sprint status, or completed stories.
- (direction) Treat Agent Node Room as a predecessor and adopted contract: preserve its transcript, Queue, Withdraw, Stop, Send now, operator attribution, control-state, and provider-steering semantics.
- (event) Production incident: restarting the API server terminated active in-process workflow executors, cut provider streams, and left workflow rows non-terminal until explicit operator recovery.
- (decision) The new feature supersedes only predecessor mechanism boundaries: API-process executor ownership, process-local reachability, server-restart loss, ephemeral queued guidance, and managed-worker 422 not_steerable_here.
- (decision) Agent Node Room remains the owner of user-visible steering semantics; Durable Workflow Runtime owns worker lifecycle, cross-process routing, execution ownership, checkpointing, recovery classification, and recovery actions.
- (capability) CAP-1 intent: workflows started through any supported entry point continue running when the API server restarts; success: an API restart during a provider turn does not stop the managed executor or duplicate the active node.
- (capability) CAP-2 intent: observers and Agent Node Room controls can reconnect to the active executor across a process boundary; success: event replay and Queue, Withdraw, Stop, Send now, and keepalive retain their existing ordered/idempotent behavior for a managed worker.
- (capability) CAP-3 intent: the system identifies the execution owner and prevents two executors from mutating one run; success: ownership transfer is fenced, stale-owner writes are rejected, and ambiguous non-terminal ownership is surfaced without an autonomous terminal mutation.
- (capability) CAP-4 intent: an interrupted in-flight node can continue from a durable provider checkpoint; success: the original provider/session is reused when available, completed nodes stay skipped, and cold resume is explicitly reported.
- (capability) CAP-5 intent: recovery never silently duplicates an external side effect; success: an unmatched tool start or otherwise uncertain effect blocks automatic replay and offers explicit continue-session, restart-from-checkpoint, or terminate choices.
- (capability) CAP-6 intent: accepted steering guidance survives control-plane and worker disruption; success: message_id deduplication, authenticated attribution, receipt order, withdraw, delivery receipts, and Never sent reconciliation remain deterministic after reconnect.
- (capability) CAP-7 intent: operators can understand and resolve interrupted execution from the inherited run and node surfaces; success: active, reconnecting, recovery-required, cold-resumed, and terminal outcomes are distinguishable and actionable without redesigning Agent Node Room.
- (constraint) All new web, adapter, webhook, and CLI dispatch paths use the managed execution boundary; legacy or externally owned executors remain explicitly unmanaged and may retain not_steerable_here.
- (constraint) A timer, last_activity_at value, or heartbeat staleness alone may not cancel, fail, abandon, or take over a non-terminal run; automatic ownership transfer needs positive owner-death evidence, otherwise operator action is required.
- (constraint) SQLite is the default and PostgreSQL is supported; schema work is additive-only in both dialects and every new NOT NULL column has a default.
- (constraint) Recovery reuses the run's original user identity, provider credentials, codebase/folder, isolation environment, branch, inputs, and frozen ENV overlay; current configuration must not silently replace the execution snapshot.
- (constraint) Provider session identifiers are resumable secrets: persist them only in the owning recovery record, encrypt where credential-grade storage requires it, and expose only masked previews in logs or broad workflow events.
- (constraint) Provider adapters must surface a recoverable session/thread identifier as soon as the provider makes it available rather than waiting only for node completion.
- (constraint) Provider resume is capability- and outcome-driven: true resume, cold fallback, unsupported resume, and unverified resume are distinct states; a fresh fallback is never reported as restored continuity.
- (constraint) Cross-process control commands carry authenticated operator identity, message_id/idempotency identity, deterministic receipt order, target execution epoch, and a typed result; stale-epoch mutations fail closed.
- (constraint) Mixed-version API servers and workers use a versioned control contract; incompatible mutations fail closed while durable observation and safe worker completion remain available.
- (constraint) A recovery attempt never replays completed DAG nodes and never treats partial provider text as a completed node output.
- (constraint) The inherited steering distinction remains: Stop interrupts the provider turn, Cancel terminates the node/run path, and recovery never implies rollback of files or external effects.
- (constraint) The feature remains single-tenant and same-install; it must not introduce tenant scoping or require a distributed multi-node scheduler.
- (decision) Spec-authored companions will hold the predecessor override map, recovery state machine and safety rules, provider recovery matrix, and restart/crash verification matrix.
- (note) Current engine evidence: web background execution is fire-and-forget inside the API process; graceful shutdown does not hand off active executors; DAG resume reconstructs completed nodes only; persisted node sessions are written only after successful node completion.
- (note) Existing leverage: CLI detached children already survive their parent process; provider contracts expose resumeSessionId and resumed outcome; all currently registered Agent Node Room providers advertise sessionResume but differ in cold-fallback observability.
- (assumption) The first release targets the five Agent Node Room steering providers—Claude, Codex, OMP, Grok, and DeepSeek—while other providers follow the same capability contract without blocking v1.
- (assumption) Managed API server and workflow workers share the single-tenant database and workspace storage; multi-host execution is outside this feature.
- (question) When owner death is positively proven and the checkpoint has no uncertain side effect, should recovery start automatically or wait for an operator Resume action?
- (question) After a host reboot, what constitutes positive death proof for a managed worker: a changed host boot identity, supervisor exit record, or both?
- (direction) Do not choose one-worker-per-run versus a persistent worker pool in the SPEC; architecture owns that implementation decision as long as the capabilities and safety constraints hold.
- (direction) Do not add a new node-room design language; recovery UI must extend the shared Agent Node Room state projection and every surface it supports at integration time.
- (decision) Coherence correction: rename CAP-3 from exactly-once ownership to fenced execution ownership so the contract does not imply exactly-once third-party side effects.
- (decision) Coherence correction: use cold-fallback, never cold-resumed, because a fresh provider session is not restored continuity.

- (event) Initial Durable Workflow Runtime spec distillation complete with two explicit open questions for downstream resolution.
- (decision) The user selected automatic recovery: when prior owner death is positively proven, a durable checkpoint exists, and no uncertain effect is present, Archon claims a new execution epoch and starts recovery without an operator Resume action.
- (decision) Positive owner-death evidence is any one authoritative proof: the supervisor recorded exit of the exact registered process identity; the current trusted host boot identity differs from the worker registration; or a trusted OS/runtime probe confirms that exact registered process identity no longer exists.
- (constraint) A registered process identity binds the host boot identity, runtime-native process or instance identifier, and immutable process-start token; PID alone, heartbeat age, timeout, probe permission failure, and unavailable evidence are ambiguous and cannot authorize takeover.
- (constraint) Automatic recovery uses an atomic fenced epoch claim, requires a durable checkpoint with no uncertain effect, and attempts strict provider resume; cold fallback, unsupported, rejected, or unverified continuity stops in recovery-required rather than executing a fresh turn automatically.
- (decision) A changed trusted host boot identity is sufficient proof that a process registered under the previous boot cannot still run; a supervisor exit record is an alternative proof, not an additional requirement, because abrupt reboot may prevent writing one.
- (event) Both initial open questions are resolved: recovery is automatic on proven-safe loss, and positive death evidence uses authoritative process identity or host-incarnation proof without timer-based inference.
- (constraint) The trusted host boot identity must be supplied by the OS or owning runtime, remain stable across Archon API and supervisor restarts, and change only when processes from the prior host incarnation cannot survive; a UUID generated at application startup is not death evidence.
- (decision) Coherence correction: CAP-4 uses the normalized provider outcomes restored, cold, unsupported, rejected, and unverified rather than the ambiguous phrase cold-started.
- (event) Update self-validation coherence PASS: all seven capabilities retain intent and testable success, automatic recovery has an explicit safety gate, positive death evidence is authoritative rather than time-based, normalized provider outcomes are consistent, and no open questions remain.
- (event) Update self-validation preservation PASS: the user's automatic-resume decision and the advised supervisor-exit, trusted host-boot, exact-process identity, atomic fencing, strict-resume, and ambiguous-evidence rules appear in the kernel, recovery contract, provider matrix, and verification matrix.

- (event) A second production failure mode was identified: restarting or cancelling a workflow can leave provider and tool subprocesses alive without a workflow owner.
- (constraint) A managed workflow cancellation is not terminal until every subprocess owned by that execution epoch has been stopped and verified absent; surviving descendants keep the run in a non-terminal cleanup state.
- (constraint) Automatic recovery or replacement must not overlap a surviving subprocess tree from the prior epoch; it may proceed only after the prior execution containment unit is proven quiescent, otherwise explicit operator resolution is required.
- (direction) Process-leak remediation is part of Durable Workflow Runtime rather than a separate hotfix: the feature must bring every Archon-owned provider and workflow subprocess spawn path under execution-scoped ownership and guarantee tree cleanup for Cancel, timeout, runtime shutdown, and failed recovery cleanup.
- (constraint) The managed-runtime guarantee is containment-honest: host execution is permitted only for spawn paths proven to remain in the execution process group or Job Object; self-daemonizing providers/tools require container hard containment, and unavailable required containment rejects execution rather than accepting an orphan risk.
