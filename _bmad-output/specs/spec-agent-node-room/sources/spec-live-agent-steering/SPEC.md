# Live Agent Steering

## Why

Opening a node of a running agent today gives a read-only transcript. An operator can watch the agent work on the wrong test suite for two minutes and do nothing but wait for it to finish being wrong.

The half that is missing is the ability to **act on the live agent**: send it a message, and interrupt its current thinking to redirect it — **without stopping the node**. Stopping the whole node already exists (the **Cancel** feature); this feature never touches the node lifecycle.

What blocks it is small, and it is on our side. Interrupting the agent already has a provider primitive — claude's `interrupt()`, or a stream-abort on any SDK — that ends the current _turn_ while the _session_ stays alive, so the operator's next message continues the same session. The one thing to get right in the engine: that same low-level abort is Cancel's and, on the node-level controller, marks the node **failed** (`dag-executor.ts:3124`) — steering must interrupt through a **separate per-turn signal** so it never trips that check, keeping the node running. Sending is not a new primitive at all: telling a running agent what to do next is an **ordinary prompt** on its live session. Both are built once and shared by every provider.

The one genuinely new engine behaviour: a steered node runs **multiple provider turns on one live session** instead of ending after the first. Everything else reuses seams that already exist.

## Capabilities

- **CAP-1** — Compose while the agent works
  - **intent:** An operator watching a running node can write a message without disturbing it.
  - **success:** The composer is mounted and enabled while the node runs, and the send control reads `Queue`. Sending holds the message; the node is untouched, no tool call is interrupted and nothing is lost. The message is delivered as the next turn when the current turn ends naturally. The interface states that the queue is per-tab.

- **CAP-2** — Interrupt the agent's thinking; the node keeps running
  - **intent:** An operator can stop the agent's _current generation_ to redirect it, without stopping the node or abandoning the run.
  - **success:** An interrupt control in the node's composer dock ends the agent's **current turn** — via the provider's own primitive (claude `interrupt()`) or a stream-abort on the executor's `AbortController` — and the **provider session stays alive**. The **node stays `running`** throughout (its agent moves to a projected `idle-after-interrupt` sub-state) — never paused, never `pending`, never `node_failed`. The transcript shows the in-flight tool call as _interrupted_ rather than _failed_. Interrupting the agent is **not** the same as stopping the node: stopping the whole node is the existing **Cancel** feature, separate and untouched. Nothing in the interface suggests the interrupt undid work already written.

- **CAP-3** — Redirect and continue on the same live session
  - **intent:** After interrupting, the operator sends what to do instead and the agent carries on from there — on the same session, in the same node.
  - **success:** Once the agent is `idle-after-interrupt`, the send control reads `Send now`. Sending delivers every queued message plus the one just typed, **in written order**, as the **next turn on the same provider session** (reusing the `attemptResumeId` re-ask seam). The node **continues** — it never "resumes" from a pause, because it never paused. Ordering is enforced by us, not assumed of the provider. Both controls follow the agent's projected sub-state, not a remembered mode.

- **CAP-4** — The exchange is part of the record
  - **intent:** Anyone reading the transcript afterwards can see what the operator said, and when, relative to what the agent did.
  - **success:** The operator's messages and the interrupted tool call appear as ordinary transcript rows in the order they happened — between the call they interrupted and the one they caused. An operator row is visibly the operator's, never mistakable for the agent's own text.

- **CAP-5** — Mid-turn delivery, as fast as each provider's transport allows
  - **intent:** The operator's message reaches a running agent without interrupting it, and sooner on a provider whose transport can take it mid-turn.
  - **success:** Sending to a running agent is an **ordinary prompt**, not a separate steer primitive — so **when** it reaches the agent is the operator's choice and only _soft-inject_ is gated by provider transport. `Queue` (the default, on every provider) delivers it as the next turn at the natural turn boundary, non-interrupting. Where a provider's open stream accepts a message mid-turn (claude streaming input), the same prompt arrives **before** turn-end with no interrupt, no interrupted tool call, and no turn-start event. claude's mid-turn path is **spike-gated** — whether `AsyncIterable` streaming input composes with the resume protocol is unverified at the pin — so the **v1 floor is interrupt + Queue** (needs no spike) and soft-inject ships when the spike clears. No provider is disqualified: interrupt-then-deliver is reachable on every one; only the _without-interrupt, mid-turn_ acceleration depends on the transport.

- **CAP-6** — The interface claims only what it knows
  - **intent:** An operator can tell whether a message merely left the browser or actually reached the agent.
  - **success:** A message reads `sent` until the provider echoes back the id we stamped on it, at which point it reads `delivered`. Correlation is by id alone. Only claude can echo the id, and that echo needs `@anthropic-ai/claude-agent-sdk` **≥ 0.3.246**; at the inherited pin **0.3.209 no provider can echo**, so today every message stays `sent` and the interface never claims `delivered`. `delivered` becomes reachable — claude-only — after that SDK bump lands.

## Constraints

- **Steering acts on the live agent, never on the node lifecycle.** _Send_ and _interrupt_ both operate on the running node's **live provider session**. The node stays `running` throughout — no pause, no `pending`, no resume, no `node_failed`. There is **no durable steering state**: no marker, no phase, no CAS, no attempt-key. Stopping the whole node is the existing **Cancel**/abort path, out of scope and untouched. (Supersedes the entire prior durable stop-and-resume model — see `ARCHITECTURE-SPINE.md` `supersedes:`.)
- **Interrupt is the provider's own primitive (or a stream-abort) on a per-turn signal, never the node-level one — and `operatorInterrupt` is a per-turn flag resolved by placement.** claude uses `interrupt()`; others use a stream-abort (codex re-runs the resumed thread — `codex.resumeThread(sessionId)`, `providers/src/codex/provider.ts:1006`). The executor's `nodeAbortController` (`dag-executor.ts:2209`) is **one-shot and Cancel's** (its `:3124` check fails the node; the re-ask loop stops on it, `:3032`). Steering must **not** abort it (that would kill the next turn's `sendQuery`, which shares the signal); it interrupts through a **fresh per-turn signal** combined with the node-level one (`AbortSignal.any`), so each new turn gets a fresh signal — this is what lets the node run multiple turns. A steering abort never trips `:3124` (Cancel-only, unchanged). The flag is resolved by **position** in the existing flow (`stream → validation → canReask :3032 → :3124 Cancel check → completion`): `canReask` must **also stop on it** (else the interrupted partial auto-re-asks the wrong work); validation is **skipped** on an interrupted turn; the flag's branch sits **immediately after** the `:3124` Cancel check, so Cancel dominates by position; and the flag is **reset at turn N+1** so a stale flag cannot mis-route a later turn. A turn that emitted a provider-normalized `result` (`dag-executor.ts:2533`) completed naturally regardless of the flag — the interrupt is spent; a stream-abort yields no `result`, which is the interrupted case. See `engine-integration.md`.
- **A steered node runs multiple provider turns on one live session — the one new engine behaviour.** It continues on the SAME session across turns, reusing the structured-output re-ask seam that already re-invokes `sendQuery` with `attemptResumeId` on the same session (`dag-executor.ts:2290`). Each delivered operator message becomes the next turn's input. **Turn-end has two causes**, discriminated by the `operatorInterrupt` flag, and they drain the queue by **different rules**: a **natural** end **auto-drains** (runs the next turn on a queued message, else completes the node when the queue is empty); an **interrupted** end produces a **partial** result (no schema-valid `output_format`) that must **not** be validated, completed, or advanced onto the DAG, and **always enters idle-await whatever the queue holds** — draining **only** on the operator's `Send now`, never automatically (this is what preserves the ratified `Send now` moment).
- **In-process only; no durable steering state.** The **in-process registry** — keyed `(runId, nodeId)`, holding the node's live session handle plus an in-memory inbound queue, valid only while the node runs _in this process_ — is the sole mechanism. A run whose executor is not in this process (CLI `--detach`) has no reachable handle, so steering is **unavailable** for it in v1 (Cancel and normal resume still work; the UI states this). A server restart drops the live session and any in-flight steer; the run resumes normally. This is the accepted v1 boundary, matching aion.
- **Delivery timing is the operator's choice; only soft-inject is provider-gated.** Three paths, and interrupt is orthogonal to all: `Queue` (default, any provider) holds the message and delivers it as the next turn at the natural boundary; `Send now` (any provider, offered only when the agent is `idle-after-interrupt`) is an ordinary prompt on the idle session → next turn immediately; **soft-inject** (where the provider folds a message into the running turn — claude streaming input at the pin; codex `turn/steer` deferred) arrives mid-turn with no interrupt. No branch holds a message "because the provider can't do better" — interrupt-then-deliver reaches every provider.
- **All of steering needs the executor in the server's process.** Web dispatch runs `executeWorkflow` in the API server's process (`server/src/routes/api.ts:3200-3228`); CLI `--detach` spawns a detached child (`cli/src/commands/workflow.ts:696-722`). Because there is no durable steering state, **every** part of steering (interrupt, Queue, Send now, soft-inject) binds to the in-process live handle — a detached run is simply not steerable in v1. (This is the reversal from the old durable model, where a DB marker reached a detached run; nothing does now.)
- **Two queues, split on send vs draft.** The **pre-send draft** is per-tab browser state (no table, no migration; the UI says per-tab). Once the operator sends, the message rides the **in-memory registry queue** on the live handle — safe there because that path exists only while the live node does, and a server death kills a `running` run along with its in-flight steer. No new table.
- **An operator message is an ordinary `text` transcript row carrying three additive `metadata` fields: `origin = 'operator'`, `operator_user_id` (the sender, for CAP-4 attribution on a multi-user install), and `message_id` (the caller-stamped id, so the client can reconcile which `sent` messages became rows).** No new table and no widened `kind` enum. The metadata schema is `.strict()`, so these are additive typed-contract fields plus a regenerated `api.generated` — not a database migration. The executor is the **sole** writer (HITL/AD-3); the row is a **receipt for the record**, not the delivery vehicle (the live session is).
- **Send and Interrupt are new routes; the queue absorbs races, only a finished node refuses.** `POST /api/workflows/runs/:runId/nodes/:nodeId/send` and `…/interrupt`, resolving identity via `resolveAuthContext` under HITL/AD-7 (not a new grant). There is **no phase/marker gate**, and **nothing is lost**. A Send that arrives while an interrupt is in flight **waits in the queue** for the operator's `Send now` (an interrupted node drains only on `Send now`, never automatically). A `Queue` message whose _generating_ turn ends naturally is auto-delivered at that boundary. The **only** refusal: a node no longer running — `node finished` → **409** (the draft stays in the browser, per `control-states.md`; teardown is the last queue check, so a message landing at the edge is caught here rather than accepted-but-never-delivered), and no live handle in this process (detached) → a clear "not steerable here". On **any** terminal (finish, Cancel, or the 30-minute idle-await fail) the in-memory queue dies with the registry, so the client reconciles its `sent` ids against the `message_id` on the operator rows actually written — **only on the node's terminal event** (`node_completed`/`node_failed`, after the executor's last write; never a live refetch, which could mis-mark a delivered message and duplicate it on resend); any unmatched `sent` id is **restored to the draft box as "Never sent"** — no message stays `sent` yet silently undelivered on any path. With two docks on one node (multi-user), the **global order is the registry's receipt order** (AD-3's "written order" is per-operator); each row's `operator_user_id` attributes it — no per-node steering lock, operators interleave attributed.
- **The dock does not appear on a finished node.** Settled by the product owner. The field and both controls are absent — there is nothing to steer, and a control that cannot act must not be drawn. Re-running a finished node would mean `workflow retry-node` (a cascading re-run behind a composer-shaped affordance), which is its own capability with its own confirmation, not this dock. One residue remains, because the operator's own words are never discarded silently: an undelivered draft box stays rendered **read-only**, stating that the node finished and the messages never left.
- **Interrupt is not undo.** Session state is saved up to the last completed tool call, but files the agent already wrote stay written — nothing is rolled back. This is not new behaviour; the existing abort path has always worked this way. The control must not imply otherwise, because an operator interrupts _precisely when they think something is going wrong_, which is exactly when they are most likely to assume it cleans up.
- **A steer delivery must not emit a turn-start event.** A stray one opens a phantom turn boundary mid-stream and corrupts the record the transcript is built from. An adapter that cannot inject without signalling a new turn holds the message for the next boundary rather than fabricating one.
- **Delivery is confirmed by id, never by matching text or timestamps.** Messages can be merged into one turn, arrive out of order, or be echoed late; text matching silently mis-attributes all three.
- **Steering is universal over a queue-and-flush floor; mid-turn is the acceleration.** Every provider delivers an operator message — at worst as the next prompt at turn-end — so none is disqualified. A provider earns _soft-inject_ (mid-turn, no interrupt) only from a transport exercised against it, never one merely advertised. Providers differ on two honest axes: **boundary granularity** (mid-turn vs turn-end) and **delivery confirmation** (CAP-6). Deliver-at-the-next-boundary is the default meaning; immediate injection is the special case.

## Non-goals

- **Cancelling the whole node.** That is the **existing Cancel/abort feature**, untouched and out of scope. This feature only interrupts the _agent's generation_ and keeps the node running; stopping the node (and the agent inside it) is a different, already-shipped control.
- **qodercli, pi, copilot and opencode.** Not in use today. Two were checked far enough to know they can join later.
- **Persisting the draft queue.** See the browser-state constraint.
- **Auto-send queue mode.** aion offers a pill that drains the queue automatically after each reply. Every send here stays operator-initiated.
- **Cancelling one individual tool call.** No provider offers it — one reports the command unsupported at that granularity, another has nothing on the wire below turn level. Interrupt is turn-level; Cancel is node/session-level.
- **Surviving a server restart mid-steer, and steering a detached run.** In-process only in v1 (see the constraint); both deferred.
- **The read-only transcript itself.** That is `spec-readable-agent-transcript`, already specced and reviewed. It already renders the interrupted-tool outcome an interrupt produces. CAP-4 is the one place this spec reaches into it — see the dependency below.

## Cross-spec dependency

CAP-4 needs a change in `spec-readable-agent-transcript`. `AgentHistoryItem` there has kinds `assistant | tool | lifecycle`, and an operator row is none of them; its AD-1 puts every row's meaning in the shared core, so the new kind and its treatment on both shells belong in that spec, not this one. Open it there before CAP-4 is built — and an operator `text` row must not reach a live transcript until that reader recognizes `origin='operator'`, else it renders as agent text.

## Success signal

An operator watches a node run the wrong test suite, types a correction, **interrupts the agent's thinking**, and sends it — and the agent **continues on the same session** against the right one, **without the node ever stopping**, without abandoning the run, and without losing the record of what happened. Reading that transcript a week later shows the wrong command, the operator's correction, and the right command, in that order.

## Open questions

- **Settled — interrupt-then-abandon fails the node after 30 minutes.** Owner-ratified: while the agent is `idle-after-interrupt` and nothing is sent, a **fresh 30-minute timer** (an explicit fail branch — **not** the existing idle-timeout, which _completes_ the node and would ship partial output) expires and the node **fails** (`interrupted by operator, no redirect received`). Because idle-await has no stream, the chunk-driven cancel-poll is dormant, so idle-await runs its **own timer-driven poll** of the run status to still honour `/workflow cancel`. Idle-await **resolves exactly once** — the first of `Send now`, that cancel-poll, or the 30-minute timer wins. The 30-minute timer is an **inactivity** timer (SC 2.2.1): a debounced, authorized composing keepalive **re-arms** it without resolving idle-await, so the node fails only after 30 minutes of genuine operator inactivity — the limit is disclosed in the dock and adjustable by activity; the ratified 30-minute value is unchanged. **Resuming a 30-minute-failed node re-runs it with a fresh session** — the interrupted agent's in-progress context is gone (there is no durable session for a steer); a builder must not try to preserve it. (Rejected: _wait-forever_ — ties up the node indefinitely, fragile in-process; _complete-with-partial_ — the do-nothing bug.)
- **Deferred — mid-turn (soft-inject) delivery to a detached run.** All of steering binds to the in-process live handle, which a detached run has no entry in. Revisit when a provider offers a channel into a session it did not spawn — grok's leader socket is the only lead found.
- **Unverified — a spike, not an assumption.** Does claude's `AsyncIterable` (streaming) input compose with the resume protocol (`SendQueryOptions.resume` + one injected user message) for soft-inject? That protocol was exercised only on a string prompt at 0.3.209. Streaming input and `interrupt()` are themselves already in 0.3.209.
- **Grok's hooks payload:** the mechanism is advertised and the handshake confirms it, but the exact shape of the text field has not been exercised. One spike settles it; until then grok is interrupt-then-continue only (no soft-inject).
- **Deferred — the `delivered` chip is gated on an SDK bump.** CAP-6's `delivered` needs `@anthropic-ai/claude-agent-sdk` ≥ 0.3.246 for the `user_message_uuid` echo; the inherited pin is 0.3.209, so `delivered` is unreachable for every provider until the pin moves. `sent` ships for all providers meanwhile. Revisit when HITL's pin advances.
