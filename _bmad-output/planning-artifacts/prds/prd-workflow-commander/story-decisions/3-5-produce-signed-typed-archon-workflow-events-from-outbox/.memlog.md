- (note by assistant) TD-03 evidence: Workflow Commander is CLI-controlled and Archon workflows run in foreground CLI, detached CLI children, and server contexts, so a server-only poller leaves CLI-only outbox rows undelivered. AD-8 forbids a new queue/runtime service. Hermes Generic Webhook accepts HTTP POST, verifies X-Webhook-Signature-V2 plus X-Webhook-Timestamp over exact raw body bytes, and deduplicates generic deliveries by X-Request-ID; absent that header it falls back to a millisecond timestamp, which is not stable across retries. Archon SQLite uses WAL/busy_timeout and transactions but no cross-process row lock; PostgreSQL supports row locking. Candidate: durable enqueue then best-effort kick of a detached drain worker, also start the same loop on server boot; claim rows atomically with a token and expiring lease (Postgres FOR UPDATE SKIP LOCKED, SQLite select plus conditional UPDATE CAS), POST event_route with stable X-Request-ID=idempotencyKey, record outcome only if claim token still owns the row, and retry ambiguous timeouts at-least-once. A lease expiry only permits reclaim; it never marks workflow state failed.
- (decision by user) TD-03 corrected and approved by deployment invariant: event delivery runs only inside the single archon serve process, which is always running. CLI and detached workflow processes may only enqueue durable outbox rows; they never host or spawn delivery dispatchers. Implement one in-process server poller with an overlap guard, immediate startup drain, periodic due-row polling, HTTP POST to binding.event_route, Hermes V2 headers, and stable X-Request-ID=idempotencyKey. Use at-least-once recovery: persist no cross-process claim/lease; a crash before delivery-result persistence leaves the row eligible for retry after server restart, with Hermes deduplication handling an ambiguous accepted request. No detached dispatcher, external queue, LISTEN/NOTIFY, FOR UPDATE SKIP LOCKED, or cross-process dispatcher election. This supersedes the prior kick-and-drain candidate.
