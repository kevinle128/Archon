Steering a running agent, from its node room

Today, opening a node of a running agent gives you a read-only transcript. This adds the other half: you can type while it works, hold the message in a queue, send it now, or stop the node. Researched against aion (client queue in useConversationCommandQueue.ts, mid-turn delivery in the Rust core) and the published Claude Agent SDK docs. Phase 1 is what ships first and works on every provider; phase 2 is drawn dimmer.

1 · The flow, in the three states it actually has

The composer is mounted and enabled the whole time — only the send button changes meaning. While the node runs it queues; once you stop the node it sends. Stopping is an explicit, visible act rather than something a button does behind your back, which matters because stopping is genuinely what happens underneath.

Stopping does not undo work already done. Session state is saved up to the last completed tool call, but files the agent already wrote stay written — nothing is rolled back. Stop means “go no further”, never “undo”, and the button must not imply otherwise. This is not a new hazard; the abort path has always behaved this way.

What you type joins the queue rather than jumping it — order is the order you wrote them, so the agent reads your correction the way you thought it. The count on the Draft box header changes from Queued to Will send, which is the one word that tells you the button in front of you is now live.

2 · The whole rule, in one table

Node stateHeaderComposerWhat sending does
runningStop nodeQueueHolds the message. The node is untouched — nothing is interrupted and nothing is lost.
stopped—Send nowDelivers every queued message plus the one just typed, in the order written, then the node resumes from where it stopped.
finished—?Open question: the node is over. Does a message re-run it, or is the composer simply absent? Not decided.

Two states, two behaviours, no hidden third path — which is the point. A “send now” offered while running would have to stop the node to work, and a button that silently stops your agent is a button that lies. Making the stop explicit costs one click and buys a UI that matches its own mechanism.

The swap is symmetric and automatic. Both controls follow the node's state, never a mode the reader has to remember setting: the moment the node resumes, the composer says Queue again and Stop node comes back to the header — the same instant, from the same signal. Nothing stays stuck in send mode after a resume, and there is no toggle anywhere for a reader to leave in the wrong position.

4 · The three states a message passes through

1 — queued, in this tab only

1Wrong suite — it's auto_retry…

2 — sent, not yet acknowledged

YouWrong suite — it's auto_retry…sending…

3 — the agent acknowledged it

YouWrong suite — it's auto_retry…delivered

State 3 requires the agent to echo back the id we stamped on the message. Without that echo the UI can only claim “sent”, never “delivered” — so the copy has to be honest about which one it knows.

deepseekyesnear-equivalentNo native mid-turn — measured, not assumed: a second prompt is rejected in 2 ms because one is already in flight. But cancel-and-continue on the same warm connection was measured at 31 ms end to end, and the partial output of the cancelled turn is kept, not discarded. The comparison that matters: the first turn spends ~3.6 s assembling context before any model call, and a cold stop-and-resume pays that again every single time the operator speaks.

Its own agent runtime does have a real steering inbox with two queues — it simply is not exposed on the protocol we speak to it over. A ceiling we could raise, not one built into it.

An earlier draft of this table said omp could not do it, reasoning from the fact that we spawn it with its standard input ignored. That inference was wrong: ignoring stdin is a consequence of invoking the CLI one-shot with the prompt in its arguments, not a limit of the CLI. Every one of these is a mode switch, never a flag flip.

Four of the five accept steering natively; the fifth gets within about thirty milliseconds of it. So “every provider can be steered” is reachable — not by bending nine different harnesses, but by building the one seam below and letting each provider plug into it the way it already knows how. The three harnesses not listed here are out of use today, and were checked far enough to know two of them could also do it when they come back.

4b · The real blocker is ours, not theirs

IAgentProvider.sendQuery() is a one-shot generator: it takes a prompt, yields events, and offers no way to push anything in after it starts. Each provider keeps its child process private inside that closure. So even where the agent on the other end accepts steering — and four of the five do — nothing in Archon can reach it.

This is the piece worth naming before any provider work begins: a steering seam on the provider interface, needed once and shared by all five, rather than five separate answers to the same question. It also reframes the phasing — phase 1 is not a workaround for weak providers, it is what ships while that seam is designed.

Phase 2 is a provider-layer change, not a UI change — the screens above do not move. The SDK exposes a caller-set message id and echoes it back, which is what turns “sent” into “delivered”; a plain string prompt, which is what Archon passes today, carries none. That is the whole reason the confirmation signal does not exist yet.
