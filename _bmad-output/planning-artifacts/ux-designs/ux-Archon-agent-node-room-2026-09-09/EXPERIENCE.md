# Archon — Experience Spine: the node room

Paired with `DESIGN.md`.
This spine specifies the behavioural delta two features add to two existing node rooms: the **readable agent transcript**, which is the half a reader reads, and **live agent steering**, the half they write from.
They share one panel, one accessibility floor, and one token set, which is why they share one spine.
The machine contracts are cited, not restated — nine tool families, the four-tier resolver, elision rules, the todo fold, task normalization, occurrence grouping and the Raw toggle in `../../../specs/spec-agent-node-room/sources/spec-readable-agent-transcript/`; the control state machine, the provider capability matrix and the engine seam in `../../../specs/spec-agent-node-room/sources/spec-live-agent-steering/`.
The approved Console, Legacy, transcript-state, and steering-state mockups are immutable evidence for every visible control, state, transition, and layout context.
This file supplies the behavior and accessibility contract for that evidence.

## Foundation

Web only.
shadcn/Radix on Tailwind v4, React 19.
Two surfaces render the same transcript:

| Surface                 | Route                                                  | Room                                                                  | Transcript component today            | Token source                    |
| ----------------------- | ------------------------------------------------------ | --------------------------------------------------------------------- | ------------------------------------- | ------------------------------- |
| Console (default route) | `/console/p/:projectId/r/:runId` (`ConsoleApp.tsx:87`) | `packages/web/src/experiments/console/components/ConsoleNodeRoom.tsx` | `inspect/ConsoleAgentHistoryList.tsx` | `experiments/console/theme.css` |
| Legacy                  | `/legacy/workflows/runs/:runId` (`App.tsx:98`+`:112`)  | `packages/web/src/components/workflows/NodeRoom.tsx`                  | `NodeTranscriptPane.tsx`              | `index.css`                     |

Both consume `buildAgentHistory()` in `packages/web/src/lib/agent-history.ts`, which gains the presentation and the folded todo state; both renderers add only markup.
Console must not import from `@/components/`, so the JSX is written twice, thin.
The room chrome around the transcript remains the HITL shell, but every visible approved control is current product behavior.
This includes state, node-kind, provider, `Re-run`, Console `Log`, Legacy `Logs`, `Graph`, `Artifacts`, and room close.
Steering adds the composer dock at the bottom of the node panel, while the shared room controller keeps those controls synchronized with execution selection, transcript, todo projection, queue, and dock.
The node panel header keeps its existing wrapping behavior; the stop control stays in the dock where it cannot wrap with header metadata.

Dark-only, because both token sources are dark-only.
The two halves differ here, and the difference is worth stating in Foundation because a reader meets it as a claim about the panel.
**The transcript half ships no schema, migration, or backend change**, so it improves every historical run the moment it deploys.
**The steering half does not have that property**: it needs an engine seam that runs multiple provider turns on one live session, an additive field on a strict transcript-metadata schema, and new send/interrupt routes bound to the in-process live handle.
Those are specified in `spec-live-agent-steering/engine-integration.md`, not here.

**One of them is a prerequisite, not a parallel task.**
Steering CAP-4 puts the operator's message in the transcript as a row, and `AgentHistoryItem` in `spec-readable-agent-transcript` has kinds `assistant | tool | lifecycle` — an operator row is none of them, and that spec's AD-1 puts every row's meaning in the shared core.
This spine owns how the row **reads** (Component Patterns → Operator text); it does not own the item kind that carries it.
That change has to be opened in the other spec before CAP-4 can be built.

Nothing **in the transcript** is a route: which rows are open is local state and survives nothing.
The panel around it is a different matter — node selection rides a `?node=<id>` query parameter (`console-run-href.ts:1-3`), so a node panel is deep-linkable even though the transcript inside it is not.
**The chips scope the transcript to one execution; they do not scroll.**
The scoping happens in two places, and reading only one of them is misleading:

- **The server does the occurrence filter — when the selected execution has an occurrence at all.**
  `occurrence_id` is optional on a node execution (`node-execution.ts:50`), and `occurrenceSelection` branches on exactly that: an execution without one yields `{kind:'node'}`, an execution with one yields `{kind:'occurrence', occurrenceId, attemptId?}` (`build-log-rows.ts:108-118`).
  Only the second puts `occurrenceId`/`attemptId` on the request (`lib/api.ts:717-719`), and only then does the client receive one execution's messages.
  `selectNodeRoomMessages` returns them in `seq` order without cutting anything, and says why in its own comment: `// occurrence-scoped: server already filtered by occurrence_id/attempt_id`.
- **So the two-occurrence view is the node-scoped one, and it is real.**
  A graph click resolves to a node-kind row when the node has one and otherwise falls back to the node's **last** row (`resolve-graph-room-row.ts:19-27`).
  A node whose executions carry no occurrence id therefore opens node-scoped, the request is unfiltered, and the transcript can span several `occurrence_id`s — which is the only state in which the occurrence header renders.
  A node whose executions are occurrence-scoped opens on its last execution, and the header never appears.
- **The client does the loop-iteration slice.**
  For `{kind:'loop_iteration'}` the same function cuts the list to the window between that iteration's `iteration_started` and its `iteration_completed` or `iteration_failed`.

**Both surfaces behave the same way.**
Console calls the identical filter on its transcript (`ConsoleNodeRoom.tsx:603`); its own copy of the module lives at `experiments/console/components/inspect/select-node-room-messages.ts`.
So the HITL README's "scoped to exactly that run" is accurate for both rooms and for both kinds of chip.

**The Story 1.7 navigator is the one control that scrolls, and it is not the `Execution` select.**
Two controls live beside the transcript and they are different kinds: `Execution` **filters** — picking an option changes which messages the server sends (and is the Story 2.10 occurrence-switching entry point for a finished iteration of a live loop — AD-16) — while the occurrence navigator **scrolls** — it moves within the messages already loaded and issues no request.
They are never merged into one select, because a control whose options both filter and scroll would lie in one direction or the other.
The navigator's contract is its own entry below (Component Patterns → Occurrence navigator); the rest of the scroll story is the shared stick-to-bottom/`scrollTop`-restore reducer (`room-scroll-follow.ts`), which navigation joins as one more explicit transition.

→ Composition reference: `mockups/key-console-node-room.html` (Console chrome, running node, one failure auto-expanded), `mockups/key-legacy-node-room.html` (Legacy chrome, completed node, two occurrences), `mockups/key-transcript-states.html` (every family, hard case, glyph, header wording, and the open Raw toggle, surface-independent).

### Context matrix

The four labels are not alternatives.
`Run N` is a repeated top-level node execution.
`Iteration N` is a loop occurrence.
`Pass N` is another provider turn inside the same occurrence.
A reason-only header is an unnumbered interruption or recovery occurrence.

The full Legacy and Console rooms render the shared queue as a full-bleed band.
The compact dock and state-review layout render it as an inset well.
The shape changes with layout context, but ownership does not: queued items are scoped to the node and shared across tabs and operators.
Only unsent composer content is `this tab only`, even when draft and queue content share one combined surface.

## Voice and Tone

Transcript microcopy is a machine reporting facts in lowercase, numbers first, `·` between facts.
It never congratulates, never explains, never wraps.

| Do                                                                                       | Don't                                                |
| ---------------------------------------------------------------------------------------- | ---------------------------------------------------- |
| `exit 0 · 38.9s`                                                                         | `Completed successfully in 38.9 seconds`             |
| `4 matches` · `11 files` · `418 lines` · `+2 −2` · `14 KB`                               | `Found 4 results!` · `Modified 2 lines`              |
| `2/5 done` · `3/6 done · 1 blocked`                                                      | `Progress: 40%`                                      |
| `1 subagent · 2m 04s` · `2 subagents`                                                    | `Spawned 2 agents`                                   |
| `running · 1m 48s`                                                                       | a spinner with no elapsed time                       |
| `Run 2 · retry` · `Iteration 3` · `Pass 2` · `recovery`                                  | `Attempt 2` · a numbered reason-only label           |
| `todo updated` (folded row headline)                                                     | repeating the checklist                              |
| `folded from 5 todo calls` · `last call wins` · `batch · 2 subtasks` · `single dispatch` | body bars that describe the UI instead of the data   |
| `Raw` · `Raw ▾`                                                                          | `Show JSON` · `Debug`                                |
| `output missing` · `output unknown` · `truncated` — the existing markers, verbatim       | inventing new failure words                          |
| `—` when a row has no badge                                                              | an empty badge slot that shifts alignment            |
| The tool name exactly as the provider sent it: `read_file`, `Edit`, `Grep`, `eval`       | prettifying, title-casing, or translating tool names |
| `gitnexus · query` for `mcp__gitnexus__query`                                            | the raw `mcp__` string                               |
| `Queue` · `Send now` · `Stop` · `Stopping…`                                              | `Send` · `Interrupt` · `Cancel` · `Abort`            |
| `QUEUED · 2` · `WILL SEND · 2` · `NEVER SENT · 2`                                        | `2 messages pending delivery`                        |
| `sent` · `delivered`                                                                     | `✓ Sent!` · a bare dot with a tooltip                |
| `stopped after the last completed tool call · files already written stay written`        | `Stopped.` · `Cancelled successfully`                |
| `this tab only` — on unsent composer content only, including a combined surface          | applying it to node-scoped queued items              |
| `couldn't send · back in the queue`                                                      | `An error occurred. Please try again.`               |
| `answer the agent's question first`                                                      | a disabled control with no reason                    |

Assistant prose is the model's own words and is not edited.
**The operator's prose is theirs and is not edited either** — not trimmed, not capitalised, not punctuated for them.
The transcript is a record of what was said, and a record that tidies its quotes is not one.

The dock speaks in the same register as the transcript — short, stating what will happen rather than reassuring — with one departure it has to make: **its controls are sentence-case, not lowercase.**
`Queue`, `Send now`, `Stop`, `Stopping…` are labels on things a person presses, and a label is a name; the transcript's lowercase rule governs reported facts, which is what everything else in the panel is.
`Stop` names an interrupt of the agent and leaves the node running; the whole-node teardown is the separate **Cancel** button, out of this dock's scope, which is why `Cancel` and `Abort` are banned as names for this control.
The one place it gets a full sentence is the stop disclosure, because that sentence exists to correct a belief the operator is likely to hold.

**Room context controls are current product behavior.**
The state control selects the complete room projection shown in the approved states and does not forge provider events.
The node-kind control selects the prompt or `loop ×3` context and synchronizes log selection, execution options, transcript, todo projection, queue, and dock.
The provider control selects the capability context shown by the room; it drives whether per-item `Send now` executes or refuses, but it never claims that an already-running provider session changed identity.
`Re-run` invokes the existing rerun owner.
Console `Log`, Legacy `Logs`, `Graph`, and `Artifacts` select their existing run surfaces.
The close control dismisses the room and returns focus to the opener.

## Interaction Primitives

Disclosure-first.
The transcript is read by scanning; opening is the exception.

- Click or tap anywhere on a row's summary toggles it.
- `Enter` / `Space` on a focused row toggles it.
- `Tab` moves through rows in document order; inside an open body the Raw button is the next stop.
- Raw is a button at the far right of the expanded body's first line, never on the collapsed row, so the collapsed row stays one scan-line.
- Failed rows open on first render; the reader may close them.
- **A reader's manual open or close outranks every automatic rule.**
  It persists across live re-renders while the node is running, and new rows arriving never reset it — including a row the transcript itself auto-opened because it failed.
  An explicit action by the reader is the strongest signal on the row, so nothing the stream does may undo it.
- Selecting another node swaps the panel content in place (room contract); open/closed state does not carry across nodes.

**The occurrence navigator commits on `change` only — one activation, one navigation.**
No key handlers are added to it: the platform's own open, commit, and cancel keys are the whole contract, so `Enter`, `Space`, arrows, and `Esc` behave exactly as the reader's platform already taught them.
Nothing is inferred from one browser's select and asserted on another.

- Committing scrolls the target heading to the top of the transcript viewport — and does not scroll at all when the heading is already fully visible — then moves DOM focus to that heading.
  The heading is programmatically focusable (`tabindex="-1"`), not a `Tab` stop: it receives focus, it does not join the order.
- The navigator sits in `Tab` order at its DOM position — after the transcript scroller, beside `Jump to latest`, before the composer dock.

**Steering is the one place the panel accepts input, and it is deliberate at every step.**

- `Enter` in the composer field inserts a newline.
  Sending is always a control press or `Cmd`/`Ctrl`+`Enter` — a bare `Enter` must not be able to reach a running agent.
  **The shortcut is stated where it is used**, on the send control's accessible name and as a hint in the composer, because an undiscoverable shortcut is the same as none for the keyboard operator it exists to serve.
  The `Cmd`/`Ctrl`+`Enter` handler is gated by the **same condition as the Send control's `aria-disabled` state** — a no-op while `Stopping…` and while blocked by a pending ask — so the keyboard path cannot bypass a block the click path refuses.
- A new message joins the **end** of the queue, never the front.
  The agent should read corrections in the order the operator thought of them.
- **The queue is per node and server-process-local; only the unsent draft is per tab.**
  A queued message rides the node's `(runId, nodeId)` registry queue: selecting another node shows that node's queue, a second tab on the same node shows the **same** queue, and it survives this tab's close — dying only on a server restart.
  The pre-`Queue` draft, by contrast, is per-tab browser state (`this tab only`).
  Both facts are stated in the interface, because either one alone would mislead.
- `this tab only` attaches only to the unsent composer content, even when a compact layout places that draft and the shared queue in one visual container.
- Every queued item keeps a visible `Send now` during generation.
  A supporting selected provider sends that item through soft-inject; a queue-only provider exposes a clear refusal through visible text and `aria-describedby`, keeps the item queued, and does not change the active turn.
- **Nothing in the dock follows the "is the agent busy" signal.**
  Controls follow node state and the draft box follows whether it holds anything.
  Busy is an async signal that flickers, and an affordance that appears and disappears under the cursor is worse than one that is simply disabled.
- Every queued item leaves the box before delivery begins, so nothing can be picked up twice; a failed delivery restores them to the front.
- Stop and send are two steps, never one.
  After an interrupt the agent is idle-after-interrupt, and the send then delivers as the next turn on the same live session — driving delivery off the back of the interrupt, before the agent is idle, is a race.
- The dock is reachable by `Tab` after the last transcript row, in document order: queue item `Send now` and delete controls, field, stop, then the dock send control.
- State, node-kind, provider, execution, `Re-run`, `Log` or `Logs`, `Graph`, `Artifacts`, and close use native button, tab, or select keyboard behavior.
  No custom arrow-key model replaces the native contract.
- Closing the room returns focus to the row or control that opened it.
  Changing node kind, provider, or execution moves focus only when the current focused element unmounts, and then moves it to the corresponding selector, never `<body>`.

**Banned in the dock:** a send control that silently stops the node; hiding per-item `Send now` because the selected provider is queue-only; an optimistic flip to `stopped` before the node says so; a `delivered` badge without confirmation of the same message id; an empty queue surface.

**Banned everywhere:** raw `JSON.stringify` as a default presentation; outcome carried by colour alone; hover-only information; a collapsed row taller than one line; a chip wider than 24 characters; the word `Attempt` anywhere in the transcript.

## Accessibility Floor

Behavioural.
Contrast measurements are in `DESIGN.md` Colors.

- WCAG 2.2 AA is the target on both surfaces.
  The accessibility review re-measured every inherited pair independently and found the `--text-tertiary` shortfall wider than first recorded — Console failed as well as Legacy, and the hovered row was worse than the resting row on both.
  **Every transcript fact therefore sits in `--text-secondary` now**, which clears the floor on both surfaces; `--text-tertiary` is left with the chevron alone, which carries no fact and is hidden from assistive technology.
  What remains short is listed in `DESIGN.md` Open Questions rather than silently accepted.
- Outcome is decodable without colour: `✓ ✕ ◐ ⚠ –` are five different shapes; `+n` / `−m` carry their sign.
- Every row is a native `<details>`/`<summary>`, so it exposes `aria-expanded` and a button role without custom ARIA.
  Support varies by browser and screen-reader pairing, so **verify the expanded-state announcement on one Windows and one macOS pairing before the row is called done** — this is a risk to close during build, not a settled fact.
- **The row's accessible name is engineered, not emergent.**
  `<summary>` builds its name from every child, so left alone a row announces its chevron first, on all of hundreds of rows.
  Three rules fix it: the chevron takes `aria-hidden="true"` (it is decoration, and `<details>` already conveys the state it duplicates); the glyph character takes `aria-hidden` with a visually hidden name beside it; and the name order is **state → tool → target → facts**.
  `·` separators are decorative and must not be the only thing between two facts.
- **Row-to-row movement is `Tab`, and arrow keys do nothing.**
  That is the native contract: `Enter` and `Space` toggle the focused `<summary>`, `Tab` moves to the next one.
  Arrow keys would need custom JavaScript and a roving tabindex, which a list of independent disclosures does not earn — the pattern applies to a composite widget, and this is not one.
- **The status glyph carries an accessible name** (`succeeded`, `failed`, `running`, `interrupted`, `unknown`) in visually hidden text.
  This is a requirement, not a preference: `◐` is announced by some screen readers as a description of the shape, which is noise rather than status, and `–` is usually not spoken at all at default punctuation verbosity — so without the name, the unknown state announces as nothing.
- **The resolved family is available without colour, on three channels.**
  It travels in the chip's accessible name (`file · read_file`) for a screen reader; as the chip's `title` for a pointer reader; and as the first word of the body bar for anyone who opens the row.
  The third is the one that always works — it needs no hover and no assistive technology — which is why the family word in the body bar is a requirement and not a nicety.
  Colour remains the fast path, never the only path.
  This is the one deliberate exception to the hover-only ban below: the `title` **duplicates** what the body bar already states in text, so nothing is reachable by hover alone.
- **Scroll anchoring and focus during a live node.**
  The transcript pins to the bottom only while the reader is already at the bottom, and otherwise holds its position — the behaviour Console already ships (`ConsoleNodeRoom.tsx:568-572`).
  An append never moves focus.
  Both are cheap now and awkward to retrofit, because a failed row renders open and inserts a multi-line body into a single scroll container (`NodeRoom.tsx:142`).
- **A focused row cannot be hidden by the panel header as the room is built today**, so SC 2.4.11 is satisfied by the layout: `LegacyNodeRoom.tsx:250-253` renders the header and the body as _siblings_, and the `overflow-y-auto` scroller is inside the body (`NodeRoom.tsx:142`).
  The header's `sticky top-0` (`NodeRoomHeader.tsx:58`) therefore sticks to a container the transcript does not scroll within.
  This is a forward guard only: if the header is ever moved inside the transcript's scroller, the row summary needs `scroll-margin-top` equal to the header height.
- **The occurrence and iteration chips keep the semantics the shipped controls already have** — `NodeRoomHeader.tsx:64-76` is a native `<select aria-label="Execution">` and `NodeRunList.tsx:28-36` is a `<nav aria-label="Node runs">` of `<button>`s with `aria-current`.
  The states-sheet mock draws them as plain non-focusable `<span>`s; **the mock is wrong and the shipped markup wins**.
  Anyone building from the mock would turn a keyboard-reachable control into a pointer-only one.
- **Occurrence headers are `h3`.**
  One level under the room's own `h2` title and the same level the pinned todo strip's label already uses (`TodoStrip.tsx:162`), so the transcript's sections slot into the room's existing outline rather than inventing a parallel one.
  The heading's accessible name is its label text verbatim — `Run 2 · retry`, not a paraphrase and never the raw `occurrence_id`.
- **Navigation moves focus deliberately — the dock's rule applied to scrolling.**
  Focus goes to the target heading, which is programmatically focusable (`tabindex="-1"`) and never `Tab`-reachable.
  If the focused heading unmounts — scope change, `Execution` filtering, Console's filters — focus lands on the navigator's select while it still renders, else on the transcript scroller, never `<body>`.
- **The select's name is its visible label.**
  `Jump to` is a real `<label>` element associated to the select, not an `aria-label` alone; the resting value is the disabled placeholder `N occurrences` with the real count; each option's accessible name is the heading's label verbatim — including its disambiguation qualifier — so option and heading can never disagree; and the select carries `aria-controls` naming the current target heading's `id` once a navigation has committed.
  **Navigation itself announces nothing** — the moved focus delivers the heading's name, which is the announcement; the polite `role="status"` region stays scoped to node transitions and failures, and row appends announce exactly as before.
- The select clears the 24px SC 2.5.8 floor through vertical padding — grown, not enlarged, the way the tool row and the Raw toggle reach it — so its painted anatomy stays the header select's.
- Focus is always visible: Legacy `{colors.focus-legacy}` 2px outline, offset −2px; Console `{colors.focus-console}` 2px outline, offset 2px.
- `Tab` order equals reading order; nothing is reachable by mouse only.
- Under `prefers-reduced-motion`, every transcript, todo, and queue chevron rotation is disabled, smooth scrolling becomes immediate, and no dock entrance, resize, or state transition animates.
  `Stopping…` remains a text change, not motion.
- At the authoritative 460px width, labels and queue items elide, the finished-iteration disclosure can wrap, and the state, node-kind, and provider control groups can wrap in source order.
  Stop and the dock send control stay on one row at opposite edges, `Go to iteration N` stays fully visible, and no room, queue, or control row creates horizontal overflow.
- A refusal is a state, not a disappearing action.
  Pending Ask, detached execution, stale retry epoch, finished node, missing live handle, and queue-only per-item send each keep the operator's content, name the reason in visible text associated with the affected control, preserve focus, and never rely on colour alone.
- **New rows are announced narrowly, through one polite `role="status"` region, and not by blanketing the transcript in `aria-live`.**
  It now serves both halves of the panel, which is a real risk worth naming: a polite region that is written twice in quick succession **drops the first message**, and Flow 4's climax is exactly that collision — the tool call settles to `interrupted` (transcript half) at the same instant the agent reports idle-after-interrupt (steering half).
  Because the interrupt is sub-second, this is up to **three writes inside one second** — `agent interrupting` → `agent idle` → the transcript's `⚠ interrupted` — and a `polite` region keeps only the message written **last**, which is AT-dependent and need not be the one that matters.
  So the rule is a **serialization mechanism, not a priority**: coincident writes are **coalesced into one composite announcement per transition**, the steering sub-state written last (`agent idle · Send now delivers`; on the auto-drain race, `turn ended before stop · 2 sent · agent generating`).
  The one message that must **never** be coalesced away is **delivery-failed-back-to-queue** — it takes its own **assertive** channel (`role="alert"`), because the spine already calls it must-not-miss and "steering wins" gives no order among steering messages.
  Beyond that it announces node-level transitions and failures only — `"run_terminal_command failed, exit 101"`, `"implement node completed"` — and leaves individual successes silent, because announcing every row of a fifty-row streaming node is worse than announcing nothing.
  The earlier plan was to announce nothing and let the panel's status badge carry it.
  That fallback does not exist: the shipped badge is a plain `<span>` (`NodeRoomHeader.tsx:78`) with no `role="status"` and no `aria-live`, so it is not announced either.
  Without this region the one event the transcript exists to surface — a failure — is the one event a blind reader never hears.
- **Target size**: the Raw toggle and the interactive tool row both clear the 24×24 minimum of SC 2.5.8 — the tool row reaches 24px through padding, so the painted box is unchanged.
  The dimensions and the reasoning are in `DESIGN.md` Open Questions → Resolved during finalize, which owns every measurement in this design.
- Text sizes stay at or above 10px, so browser zoom is the reader's remedy; the row does not reflow below that.
  Page zoom scales the panel and the text together, so nothing drops; only a raised root font size or text-only resizing puts the row under pressure, and then the body bar is what holds the dropped facts.

### The dock

Steering adds four status channels to a panel whose whole guarantee is that status never rides on colour.
Each is answered here.

- **Five dock changes are status messages and need SC 4.1.3 semantics, not just visible text.**
  A message moving to `sent`, a message reaching `delivered`, a delivery failing back into the queue, the send being blocked by a pending ask, and **the 30-minute idle-fail** all change state without moving focus.
  Each is announced rather than left to a visual diff — the delivery failure on the assertive channel above, the rest through the polite region.
  The failure case is the one that must not be missed: an operator who pressed `Send now` and heard nothing will press it again.
  The 30-min-fail gets **distinct copy that names its cause** — `node failed · interrupted with no redirect · none of this was sent` — so it reads as neither a crash nor a normal completion, and it inherits the finished-node focus + read-only-box treatment.
- **The send control's two readings are its accessible name**, so the change is exposed for free — but a name that changes under a reader who is not looking at it is not an event.
  The agent's sub-state transition is what gets announced, through the same polite `role="status"` region the transcript already owns, and each carries its consequence rather than only naming the agent: `agent interrupting` (only when `Stopping…` is shown), `agent idle · Send now delivers`, `agent generating` — the node staying `running` throughout.
  Three events, added to a region that already announces node transitions and failures, rather than a second live region competing with the first.
- **Queue depth rides the send control's accessible name** — `Queue message, 2 waiting` — for as long as a control exists to carry it, because the channel it backs up is the draft box's _absence_, and absence cannot be announced.
  **On a finished node no control is left**, which is the one state where an operator most needs to hear that two messages never went: there the count rides the read-only list's own name instead.
- **The composer field carries a real label, not a placeholder.**
  A placeholder is not a label — it disappears on first keystroke and several screen readers never announce it.
  The field's accessible name states the node it writes to, so a reader landing in it by `Tab` knows what they are about to steer.
- **The draft box is a labelled list, not a stack of divs.**
  It exposes a list with an accessible name carrying the count and the mode — `Queued messages, 2` / `Will send, 2` / `Never sent, 2` on a finished node — and each item is a list item whose own name is its text plus its per-item controls, or its text alone once the list is read-only.
  Without that, the box announces as loose prose and the count exists only in the heading a reader may have skipped past.
- **Per-item `Send now` has one accessible contract in every provider state.**
  Its name starts with `Send now` and the message excerpt.
  A queue-only provider adds an associated refusal description, keeps the control focusable with `aria-disabled`, and suppresses dispatch.
  A supporting provider activates only that item.
- **`sent` and `delivered` are words.**
  The success colour on `delivered` is added on top of the word, never instead of it — the same rule the status glyph follows.
- **Authorship of an operator row travels on the `operator` role label**, not on the text strength that makes it scannable — and on a node with more than one operator the label names the **sender** — resolved to the `users` display name for that `operator_user_id`, with a short id as fallback only when no name exists — not a bare `operator` and never a raw id, so two operators on one node stay told apart by name.
  Strength is the fast path; the label is the one that always works.
- **Two build-verification points, not design changes:** the uppercase draft-box headers (`QUEUED` / `WILL SEND` / `NEVER SENT`) and the `operator` / `assistant` role labels must be CSS `text-transform: uppercase` over lowercase DOM text — some AT spells literal DOM capitals letter-by-letter; and any `Cmd`/`Ctrl`+`Enter` hint appended to the send control's accessible name keeps the visible word (`Queue` / `Send now`) at the **start** of that name, or SC 2.5.3 and speech-input targeting break.
- **Focus must survive the stop, and it is dropped at the earlier of the two transitions.**
  There are two, and the dangerous one is not the obvious one.
  `running → stopping` is where it goes: the native `disabled` attribute blurs the element that carries it, so the operator who just pressed `Stop` by keyboard lands on `<body>` — and `Tab` from `<body>` restarts at the top of the document, putting the entire transcript between them and the dock they were working in, however brief the interrupt is.
  So **whenever `Stopping…` is shown it is `aria-disabled` with a suppressed handler, never the `disabled` attribute.**
  Then at `stopping → stopped`, when the control unmounts, focus moves deliberately to the send control — which is only possible because the first fix kept it there.
  **Both are build requirements.**
  They manifest only for someone driving the dock by keyboard, which is exactly why nobody would find them by clicking through it.
- **The control focus lands on has just changed what it does.**
  That same moved focus arrives on a control whose label flipped from `Queue` (holds a message, harmless) to `Send now` (delivers everything and resumes the node).
  The dock's focus ring is therefore not optional decoration: all four focusable dock elements carry the fixed `{colors.focus-legacy}` / `{colors.focus-console}` ring — **6.8:1 / 4.6:1**, clearing SC 1.4.11 — and on Legacy a dock control overrides shadcn's `focus-visible:ring-ring/50` rather than inheriting it at 2.3:1.
  An operator who cannot see where focus is, on a control that silently changed meaning, presses `Enter` and delivers to a live agent.
- **When `Stopping…` is shown it may dim but may not vanish, and the floor is `--text-secondary`.**
  It is `aria-disabled`, not `disabled` (see above), so it stays focusable — and SC 1.4.3's exemption for an inactive component no longer applies to it.
  The dim therefore has to clear 4.5:1 like any other text: `--text-secondary` measures **5.3:1 / 7.9:1**, where tertiary would be **2.3:1 / 3.9:1**.
  Removing the control instead is the other wrong answer — it moves every sibling under the pointer and loses the reader's place.
- **Target size**: the dock's own controls — stop, send, and the composer field — take a `{spacing.control-min-h}` 32px floor, clearing SC 2.5.8's 24px with room.
  This is the one place in the panel that does _not_ settle for the tool row's 24px target, and it should not: 24px suffices for a row that is a disclosure in a dense list, but a control that stops an agent is not.
  **A draft item's keep and delete are the exception at 24×24**, grown on padding the way the Raw toggle is — an 11px row cannot carry a 32px control without becoming a card, and these two actions are neither destructive to the run nor hard to repeat.
- **The dock grows, and growth is the same hazard as overlap.**
  A draft box appearing, or the field expanding, shortens the transcript's viewport from below — which can scroll a focused row out of view even though the dock never overlaps it.
  Growth therefore preserves the scroll position of a focused row, the same way the transcript already pins to the bottom only when the reader is already there.
- **Being a sibling puts the dock outside the room's landmark**, which is the price of the SC 2.4.11 answer below.
  The dock is therefore inside whatever region wraps the node panel as a whole, not outside both — a write surface that belongs to no landmark is one a reader navigating by region will never be handed.
- **The dock must not obscure a focused transcript row (SC 2.4.11).**
  This is the sticky-header analysis at the other edge of the panel, and it has the same answer: **the dock is a sibling of the transcript's scroller, never a child of it** — exactly as the header already is (`LegacyNodeRoom.tsx:250-253`, scroller at `NodeRoom.tsx:142`).
  A dock rendered inside the scroller would overlay the last row, and the last row of a running node is the one the reader is watching.
  If it is ever moved inside, the row summary needs `scroll-margin-bottom` equal to the dock height.
- **Contrast is measured, not inherited, and the measuring changed the design.**
  Every dock pairing is now in `DESIGN.md` Colors with a number.
  An earlier draft of this line claimed the send control's pairing was "already measured" because the control inherited a shipped button; it was in no table, and the shipped button it inherited measures **3.1:1** on an 11.5px label.
  The send control is bordered on both shells for that reason.
  Two cells stay bold and both have a disposition there, neither of them silence.
- **The inactivity rule is visible and adjustable.**
  Idle-after-interrupt states `no redirect ends this node after 30 min of inactivity · typing keeps it open`.
  Authorized typing activity sends the debounced composing keepalive and re-arms the timer.
  `Send now`, the cancel poll, or timer expiry resolves the idle wait exactly once.
  No countdown runs.
  Expiry announces `node failed · interrupted with no redirect · none of this was sent`, restores unmatched content read-only, and moves dock focus to the last transcript row.
- **Two shells means one semantic test matrix.**
  Console and Legacy must assert the same state transitions, context labels, queue ownership, provider capability/refusal behavior, keyboard activation, focus recovery, accessible names, live announcements, 460px layout, and reduced-motion behavior.
  Only tokens, shell chrome, and `Log` versus `Logs` differ.

## Occurrence grouping

Occurrence grouping keys on `occurrence_id`, never `attempt_id`.
Provider-turn segmentation is nested inside an occurrence and comes from the executor's turn boundaries.

| Context                                             | Header        | Number rule                                                   |
| --------------------------------------------------- | ------------- | ------------------------------------------------------------- |
| Repeated top-level node execution                   | `Run N`       | `N` is the top-level execution ordinal                        |
| Loop occurrence                                     | `Iteration N` | `N` is the loop occurrence ordinal                            |
| Another provider turn inside the same occurrence    | `Pass N`      | `N` is the provider-turn ordinal within that occurrence       |
| Interruption or recovery occurrence without ordinal | reason only   | No number is invented; the known reason is the complete label |

`Run`, `Iteration`, and `Pass` are different levels of context and can appear in the same transcript.
`Attempt` remains forbidden because `attempt_id` is finer than these reader contexts and the label would lie.

**Colliding base labels are disambiguated, never left identical and never repaired with a raw id** (adopted 2026-09-19, issue #180 decision B4).
Within a maximal set of groups that derive the same base label, each group takes the **first** qualifier that makes it unique inside that set:

1. **Route activations** — when the colliding executions carry distinct `route_activation_seq` values, the base label gains ` #N`, the suffix the execution row already wears (`build-log-rows.ts:100`).
   Two activations at retry epoch 0 read `Run 1 #1` and `Run 1 #2`.
2. **Nested loops** — when colliding `Iteration N` labels come from a `loop_ancestry` deeper than one entry, the label expands to the ancestry's iteration path root→leaf: inner iteration 3 under outer iterations 1 and 2 reads `Iteration 1 › Iteration 3` and `Iteration 2 › Iteration 3`.
   When the iteration path alone still ties — two different loop bodies running the same numbers — the nearest ancestry `node_id` that differs is appended: `Iteration 1 › Iteration 3 · fetch_pages` against `Iteration 1 › Iteration 3 · parse_pages`.
3. **Residual ties** — a collision the typed fields cannot separate (same epoch, same activation sequence, same ancestry; only `occurrence_id` differs) falls back to `· occurrence K`, `K` the group's 1-based order of first appearance among all groups in the transcript, applied to every tied member past the first position: a leading set reads `Run 1`, `Run 1 · occurrence 2`, `Run 1 · occurrence 3`.

Reason suffixes always trail the qualifier — `Run 1 #2 · retry`, `Run 2 · occurrence 2 · failed` — so the suffix vocabulary never moves.
The navigator's option text and each option's accessible name are the identical final string, so a heading and its option can never disagree.
`occurrence_id`, `attempt_id`, and provider names never appear in either.

Inside a group, assistant text and tool rows interleave in `seq` order.
Header options as rendered for the review: `mockups/key-transcript-states.html` §E.

## Elision and badge priority

A row is one line, so three things give way in a fixed order.

1. **Chip** caps at `{spacing.chip-max}` and ellipsises inside the pill.
2. **Headline** absorbs the remaining pressure: path kind elides in the middle so the filename survives; text kind elides at the end.
   The elision is **CSS on a two-span headline** — a head that may shrink and a tail that may not, per `DESIGN.md` Shapes — so it truncates the _rendering_ only.
   The full path stays in the DOM, which is what keeps it readable by assistive technology and selectable for copy.
   A produced string with characters cut out would destroy the path for every reader at once, and is not what this rule means.
3. **Badges** drop duration first; exit code, match count, file count, and `+n −m` are kept.

**Any badge dropped under pressure must still appear in the body bar.**
The mocks already do this — the row badged `exit 101 · 41.2s` repeats `exit 101 · 41.2s · cwd …` inside its body — but it has to be a contract rather than a coincidence, because it is what turns "the duration badge drops" from information loss into one disclosure away.
Dropping a fact with no path back to it would be a reflow failure at narrow widths.

Hard cases 1–4 in `mockups/key-transcript-states.html` §C show each rule under load.

### Flow 1 — Kevin watches a node run (Console, `mockups/key-console-node-room.html`)

1. Kevin opens `speckit-ralph-native-feature` at `/console/p/<project>/r/run_d9556522f45a`; the run is Running and the `implement` node reads `running · 14m 07s · run 2`.
2. They click the node; the panel opens with the transcript under `Run 1`.
3. They scan seven collapsed rows without opening any: two `read_file` rows with their filenames intact, a `grep`, a `glob`, a `todo updated`, a `task` row reading `2 subagents · 2m 04s`, a `search_replace` with `+14 −3`.
   They open the `task` row, because a dispatch is the one row whose headline cannot say what happened inside it: the batch context reads as markdown, then one card per subtask, each with its agent name in semibold, its subtask name, and its prompt.
   `TaskSubtask` carries no per-subtask outcome, so the cards say what was dispatched, never how each one ended — the row's own glyph is the only status.
   They close it again.
4. **Climax:** the eighth row is already open — `✕ run_terminal_command cargo test … exit 101 · 41.2s` — and beneath it the terminal body shows the panic, `left: 31 right: 30`.
   They know what failed and why without a single click.
5. The `Run 2 · retry` header follows, then the assistant's one-line diagnosis, the `edit` row with `+2 −2`, the same test now `exit 0`, an `eval` row.

   They leave it open in a tab.

Nothing is fabricated.

### Flow 2 — Kevin reads a finished node (Legacy, `mockups/key-legacy-node-room.html`)

### Flow 4 — Kevin steers a node that is doing the wrong thing (Console, `mockups/key-steering-dock.html`)

1. Kevin has the `implement` node open and running.
   They are watching rows append: a `read_file`, a `grep`, then `◐ run_terminal_command cargo test --workspace … running · 12s`.
2. That is the wrong suite.
   It will take four minutes and tell them nothing.
   They type into the composer without touching anything else — the node keeps working, no row changes — and press `Queue`.
   The full-room queue band appears between the todo strip and dock reading `QUEUED · 1`; the accepted item is server-side and shared for this node.
   `this tab only` stays attached only to text that has not left the composer.
3. They remember a second thing and queue that too.
   `QUEUED · 2`.
   The new message sits at the bottom after the first.
   Each item shows `Send now`; the selected provider capability decides whether it soft-injects or returns the visible queue-only refusal.
4. They press `Stop`.
   If a `Stopping…` transient shows it is momentary.
   Nothing else moves — no progress bar, because nothing is being tracked — and the panel announces `agent interrupting` once.
   The interrupt lands in well under a second.
5. **Climax:** the running row settles to `⚠ run_terminal_command cargo test --workspace … interrupted`, not a red failure — the agent was stopped, it did not fail.
   The stop control is gone, the send control now reads `Send now`, the draft box header has flipped to `WILL SEND · 2`, and one line under it states what just happened: `stopped after the last completed tool call · files already written stay written`.
   They had half-assumed the stop would undo the file it wrote a minute ago.
   It says otherwise, in text, at the exact moment they would have assumed wrong.
6. They type the third and most important correction into the field and press `Send now`.
   All three leave the surface in receipt order and appear in the transcript as `operator` rows, each badged `sent`.
   A row changes to `delivered` only after its provider confirms the same caller-stamped id.
   G1 makes that Claude confirmation current behavior; providers without confirmation stay at `sent`.
7. The agent starts generating again.
   `Stop` returns to the dock, the send control reads `Queue` again, and the next row is `◐ run_terminal_command cargo test -p archon-workflows …` — the right suite.
   Reading this transcript next week shows the wrong command, their three corrections, and the right command, in that order.

Failure: they press `Send now` on a node that is itself parked at an unanswered ask → the control is `aria-disabled` and says `answer the agent's question first`, because a node parked at an ask is `pending`, not live-steerable, so there is nothing live for the steer to reach until the ask is answered.
A _sibling_ node's ask does not do this — this node stays `running` and steerable.
Failure: delivery drops → the messages return to the **front** of the box and it reads `couldn't send · back in the queue`.
His words are never lost to an error.
Race: the turn ends on its own before the stop lands → the interrupt is spent, so it is a natural end (AD-4).
With his two messages still queued they **auto-drain** as the next turn and the agent keeps going; only an _empty_ queue lets the node finish, resolving the dock to its finished-node treatment with anything unmatched shown read-only as `NEVER SENT`.
Nothing is delivered to a node that stopped listening, and nothing queued is stranded while it still runs.
