- (direction) Deliver both a terse architecture spine and a detailed solution design serving implementers, technical reviewers, and production operators.
- (constraint) The Durable Workflow Runtime SPEC and its four authored companions are the binding feature contract for CAP-1 through CAP-7.
- (constraint) Inherit the parent Live Agent Steering ports-and-adapters paradigm and preserve provider ports, workflow-engine ownership, core persistence, server transport, and shared web projection dependency direction.
- (constraint) Inherit Live Agent Steering AD-1: Queue, Withdraw, Stop, and Send now act on the live provider session while the node remains running; Cancel remains the separate teardown path.
- (constraint) Inherit Live Agent Steering AD-2: Stop ends the current provider turn, not the provider session; the per-turn interrupt seam stays distinct from node-level Cancel.
- (constraint) Inherit Live Agent Steering AD-3: Queue and Send now remain ordinary prompts with operator-selected delivery timing; provider capability gates only soft-inject.
- (constraint) Inherit Live Agent Steering AD-4: steered nodes use multiple turns on one session, partial interrupted output never advances the DAG, and idle-after-interrupt keeps its established semantics.
- (constraint) Inherit Live Agent Steering AD-6: the executor remains the sole writer of attributed operator transcript rows and message_id remains the reconciliation identity.
- (constraint) Inherit Live Agent Steering AD-7 and AD-8: steering fabricates no turn-start event and delivery status never claims more than provider evidence proves.
- (constraint) Inherit Live Agent Steering AD-9: generating and idle-after-interrupt are projected substates of a running node and every shell consumes the shared projection.
- (constraint) Inherit Live Agent Steering AD-10: operator transcript meaning remains owned by the Agent Node Room/readable-transcript contract rather than being redefined here.
- (constraint) Inherit Live Agent Steering AD-11: authorized steering commands preserve authenticated attribution, server receipt order, race handling, and terminal Never sent reconciliation.
- (constraint) Inherit Live Agent Steering AD-12: operator display names are resolved server-side at read time and are not denormalized into durable command metadata.
- (decision) The successor feature explicitly supersedes Live Agent Steering AD-5 only for Archon-managed executions: live handles and guidance must become reachable across the API process boundary and survive a control-plane restart; legacy or external executors may remain not_steerable_here.
- (constraint) A normal ./scripts/deploy-pm2.sh invocation is the production restart boundary: it may replace the API process but must leave active managed workers alive and reconnectable.
- (constraint) Automatic recovery requires authoritative owner-death evidence, a clean durable checkpoint, no uncertain effect, an atomic new execution epoch, and strict provider resume; timer or heartbeat staleness alone never authorizes takeover.
- (constraint) The design remains same-install, single-host, single-tenant; SQLite and PostgreSQL schema changes are additive-only, and the API/worker protocol is versioned for mixed-build reconnect.
- (version) Reality check 2026-09-20: the development host has PM2 6.0.14 installed; official PM2 documentation identifies major 7 as current, so the design cannot depend on undocumented v6-only child-process behavior.
- (constraint) Official PM2 behavior: restarting an ecosystem file restarts every app declared in it unless --only selects names; PM2 also manages process trees, so an API-spawned detached child is not a trustworthy survival boundary for PM2 restart.
- (constraint) Current web dispatch pre-creates the run then calls executeWorkflow fire-and-forget inside the API process; SIGTERM shutdown closes adapters, telemetry, and the DB pool but provides no executor handoff.
- (constraint) Existing CLI detach proves a reusable process-per-run seam: Node spawn uses detached process groups, ignored stdio, startup acknowledgement, per-run logs, and re-invokes the CLI without --detach, but it has no cross-process steering or durable ownership registry.
- (question) Coaching fork 1: choose the managed execution topology—one separate runtime process hosting all concurrent runs, or a stable PM2 runtime supervisor with one isolated worker process per workflow run.
- (constraint) The runtime must bound CPU/process growth: one-process-per-run, if chosen, means one process per active run only and a supervisor-owned maximum active-worker count; excess runs remain durably queued rather than spawning unbounded processes.
- (constraint) A workflow worker does not reserve a CPU core and is mostly idle while waiting on provider/network/subprocess I/O; per-run isolation mainly adds Bun startup, memory, file-descriptor, and scheduling overhead, while provider and script work consumes similar CPU under either topology.
- (constraint) The existing concurrency.maxConversations default 10 is an API-process-local conversation lock; it cannot be the durable worker scheduler because it disappears on API restart and also mixes chat handling with workflow execution.
- (question) Coaching fork 1 refined by the CPU requirement: choose a bounded number of isolated per-active-run workers with durable queueing, or one shared runtime process with lower overhead but all-runs failure blast radius; choose the worker-slot count separately from the topology.
- (constraint) Cancellation is complete only after Archon has fenced the execution epoch, stopped the execution-owned subprocess containment unit, escalated from graceful termination when necessary, and verified that no process in that unit remains alive.
- (constraint) Worker death and subprocess-tree quiescence are separate facts: surviving provider, shell, script, git, test, or tool descendants block terminal cancelled state and block replacement or automatic resume until cleanup is proven complete.
- (constraint) Process cleanup must target a verified execution-scoped containment identity, not a stale PID or broad name pattern; ambiguous identity must fail closed and surface operator action rather than risk killing an unrelated process.
- (question) Topology decision now includes subprocess ownership: adopt a bounded per-active-run execution capsule whose worker is the leader of one OS containment unit and whose descendants cannot escape it.
- (decision) AD topology choice adopted by the user: managed execution uses a bounded per-active-run execution capsule. A stable runtime supervisor owns a configurable worker-slot limit and durable queue; each admitted run receives one isolated worker that leads a verified OS containment unit for all provider and tool descendants. This binds dispatch, cancellation, recovery, and resource control and prevents unbounded process growth, cross-run cleanup, and shared-runtime blast radius.
- (constraint) The operator contract remains one command: ./scripts/deploy-pm2.sh deploys both the API and execution-runtime release. Operators are not required to run a separate runtime deployment or maintenance command; process replacement must be orchestrated safely behind that script.
- (question) Recommended deployment refinement: use versioned rolling runtime generations so the normal deploy starts the new runtime generation for newly admitted runs while the prior generation drains its existing execution capsules and exits only when empty; confirm this instead of delaying all new runs until one supervisor can restart.
- (constraint) Current deployment is mutable source mode: deploy-pm2.sh installs dependencies and builds the web UI in the shared checkout, then PM2 runs Bun against packages/server/src/index.ts and restarts the single ecosystem app. This cannot safely pin old and new runtime generations by itself.
- (constraint) Every admitted execution capsule must be pinned to an immutable runtime release_id and launch artifact for its whole lifetime. A server deploy may advance the API/current release and admit new runs on the new runtime, but it must not overwrite or garbage-collect artifacts referenced by active capsules.
- (constraint) New API and runtime generations must coexist with prior active generations through the versioned control contract and additive database schema. Incompatible mutations fail closed; old workers may complete and remain observable, and an old release is reclaimable only after durable ownership records prove no active capsule references it.
- (decision) Scope adopted by the user: subprocess ownership and leak prevention ship with Durable Workflow Runtime, not as a separate implementation track. The architecture binds every engine-owned provider, bash, script, until_bash, git, test, and tool descendant to the execution capsule lifecycle across Cancel, timeout, runtime shutdown, and recovery.
- (direction) Transcript tail-first loading remains independent from Durable Workflow Runtime because it changes message pagination and room rendering rather than execution ownership; route it through its own downstream feature workflow unless the user explicitly merges that scope later.
- (decision) Rolling runtime generations are adopted. A normal deploy starts the new API and runtime generation for newly admitted work; prior generations stop accepting new runs, retain ownership of their existing execution capsules, and exit only after draining. A durable global admission limit spans overlapping generations, and immutable release artifacts remain pinned until no active capsule references them.
- (constraint) Current live steering is a process-local singleton: API routes synchronously mutate NodeSteeringHandle instances and return not_steerable_here when the handle is in another process. Durable Runtime must replace this reachability mechanism without changing the inherited enqueue, withdraw, ordering, idempotency, and terminal-gate semantics.
- (constraint) SQLite remains the zero-infrastructure default and has no LISTEN/NOTIFY; PostgreSQL notification is an optional wake-up optimization already used with polling as a backstop. The durable command and scheduling authority therefore cannot require Redis, PostgreSQL, or another external broker.
- (question) Choose the cross-process command fabric: a database-authoritative durable inbox with one supervisor poller and optional wake-up hints, or a socket/RPC-authoritative path supplemented by persistence for recovery.
- (decision) The database-authoritative durable inbox is adopted for scheduling and cross-process commands. API, adapters, and CLI persist an authenticated epoch-bound command before returning an accepted receipt; one runtime-supervisor poller claims and routes commands to local capsules. PostgreSQL notification or local IPC may wake the poller, but lost wake-ups are harmless because bounded polling is the backstop and no external broker is required.
- (question) Choose the containment promise: host-native execution capsules using POSIX process groups and Windows Job Objects with an explicit self-daemonizing escape limitation, or container isolation for every run to enforce a hard kill boundary at greater resource and provider-integration cost.
- (decision) Hybrid containment is adopted. Host-native capsules are the default and use a dedicated POSIX process group or Windows Job Object with TERM, bounded grace, KILL, and quiescence verification. Every spawn adapter must be certified tree-contained and must not detach descendants; providers or tools that may setsid, double-fork, or otherwise escape are capability-gated to container hard containment, and fail fast when that boundary is unavailable rather than weakening the cleanup guarantee.
- (question) Choose durable dispatch authority during rolling generations: one database-fenced active dispatcher generation with older generations drain-only, or multiple supervisors competing for queue claims through per-item fencing.
- (decision) A single database-fenced active dispatcher is adopted. The newest runtime generation alone admits queued runs; prior generations are drain-only and retain only their existing execution ownership. Dispatcher handoff is explicit or based on authoritative process-death proof, never heartbeat age alone, and the durable global slot ledger includes capsules across all live generations.
- (constraint) A capsule-count limit alone does not bound execution load: the DAG executor runs independent nodes in a layer concurrently through Promise.allSettled, and fan_out independently defaults max_parallel to 5. One admitted workflow can therefore create several simultaneous provider and subprocess activities.
- (question) Choose resource governance: combine the bounded active-capsule limit with a global fair permit budget for top-level provider and executable-node activities across every runtime generation, or limit only active workflow capsules and leave each workflow's internal DAG/fan-out concurrency unconstrained globally.
- (decision) The user selected capsule-only resource governance for simplicity. Durable Runtime bounds the number of active execution capsules globally across rolling generations but does not add a global activity-permit scheduler; existing DAG-layer parallelism and fan_out.max_parallel continue to govern concurrency inside each admitted workflow.
- (constraint) The active-capsule limit controls worker count, startup/memory overhead, and coarse load but is not a hard CPU or subprocess-concurrency limit because one admitted workflow may execute several parallel nodes and provider-created descendants. Documentation and observability must state this honestly; revisit an activity budget only if production measurements show the simpler control is insufficient.
- (question) Choose the conservative default active-capsule limit now that internal node concurrency remains unchanged: 2 for the production 10-core Mac Mini, or 4 for higher workflow throughput with greater peak load; both remain operator-configurable.
