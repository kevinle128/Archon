# Technology and Current-Version Gate Review

**Review target:** `../ARCHITECTURE-SPINE.md`  
**Evidence date:** 2026-09-21  
**Lens:** named technologies, committed versions, repository/runtime fit, and claims that depend on current upstream behavior

## Verdict

**REVISIONS REQUIRED.** The named PM2 and provider-SDK versions are accurate, the PostgreSQL coordination fit is grounded, and the public PM2 `--only` mechanism supports the proposed API-only restart. The architecture is not ready to approve on its default SQLite path, however: the observed Bun 1.3.14 host exposes SQLite 3.51.0, while the design introduces multiple WAL writer processes and SQLite documents a WAL-reset corruption race through 3.51.2 under that topology. The spine also needs to distinguish current observations from future guarantees for the Bun runtime pin, strict provider-resume outcomes, and host containment proof.

This verdict does **not** recommend upgrading every dependency to the latest release. Upstream versions below are a current reference point, not an automatic target. The smallest safe target is the exact version already tested by Archon unless a finding requires a newer fixed capability.

## Findings

### HIGH-1 — Observed SQLite version is unsafe for the proposed multi-process WAL topology

**Problem:** The spine commits SQLite as the default shared durable coordination plane while moving each managed run into its own process. On the observed production-like host, `bun:sqlite` reports SQLite 3.51.0.

**Evidence:** The existing adapter forces WAL (`packages/core/src/db/adapters/sqlite.ts:43-52`). SQLite's official WAL documentation says the WAL-reset corruption bug affects versions 3.7.0 through 3.51.2 when two or more connections in separate threads/processes write or checkpoint concurrently, and that it is fixed in 3.51.3 and later ([WAL documentation, §11](https://www.sqlite.org/wal.html)). The new topology creates exactly the prerequisite that the current mostly single-process architecture avoids. The system `sqlite3` CLI also reports 3.51.0, but the decisive result is the query executed through the actual `bun:sqlite` driver.

**Impact:** This is a durability-integrity risk in the component declared to be the command, ownership, checkpoint, and projection authority. “Rare” is not an acceptable silent assumption for the coordination plane.

**Smallest fix to the spine:** Add a Stack/AD-2 admission requirement that SQLite-managed execution starts only when a runtime query proves a fixed SQLite build (at least 3.51.3, or an explicitly verified fixed backport). Record the exact Bun and SQLite versions in the immutable release manifest and fail closed when the release/runtime pair does not meet that gate. Do not infer SQLite safety from the Bun semver or release notes alone. Keep SQLite as the user-selected default; this is a minimum safety preflight, not a request to replace it with PostgreSQL.

### MEDIUM-1 — The Bun Stack row conflates compatibility, tested baseline, local observation, and future pinning

**Problem:** “Repository engine `^1.3.5`; authoring host `1.3.14`. Worker artifacts pin their build/runtime identity” reads as one coherent version contract, but those are four different states.

**Evidence:** The manifest permits Bun versions from 1.3.5 up to (but excluding) 2.0.0; CI and Docker use 1.3.11; the current host runs 1.3.14; the PM2 deploy script chooses the ambient executable. No repository artifact currently pins the host worker runtime.

**Impact:** A release-pinned TypeScript source tree can still run under a different Bun/embedded-SQLite build after a host upgrade, defeating AD-8's reproducibility and making mixed-release recovery behavior depend on ambient state.

**Smallest fix to the spine:** Split the Bun Stack entry into (1) declared compatibility, (2) tested build baseline, (3) observed host, and (4) target release-runtime rule. Make the target rule explicit: each release records an exact Bun version plus executable/build identity and the supervisor must launch or validate that exact runtime. The architecture need not choose Bun 1.4.2 merely because it is latest.

### MEDIUM-2 — SDK resume seams exist, but the current adapters do not yet provide the strict outcome contract

**Problem:** The Stack wording “recovery capability remains adapter-outcome driven” can be read as an existing fit. The SDKs expose resume entry points, but Archon's current normalized outcome is only `resumed?: boolean` (`packages/providers/src/types.ts:350-359`).

**Evidence:** Codex's current general path catches a `resumeThread` failure and starts a fresh thread before yielding `resumed: false`; that is intentionally incompatible with automatic strict recovery. Claude currently marks a requested resume as successful when it reaches the result stream, based on the adapter's “resumes-or-errors” assumption. Official SDK documentation confirms the resume inputs, not Archon's five-way `restored | cold | unsupported | rejected | unverified` proof contract. The companion provider-recovery matrix correctly identifies these gaps.

**Impact:** Implementers could reuse the general chat path and accidentally perform a substantive cold turn during automatic recovery, violating AD-6.

**Smallest fix to the spine:** Change both SDK Stack notes to say that the pinned SDK provides a continuity seam, while durable recovery **requires a new strict adapter path and normalized outcome contract**. Point explicitly to `provider-recovery-matrix.md`; state that the existing general fallback path is not the recovery path. No SDK upgrade is required to make this wording honest.

### MEDIUM-3 — Process-group creation is proven; exact containment proof and Windows support are not selected technologies

**Problem:** AD-4/AD-5 promise exact, PID-reuse-safe termination and quiescence on POSIX and Windows, but only the POSIX group-creation primitive is currently grounded.

**Evidence:** Bun documents and the local host demonstrates separate-process-group spawn. The repository has no exact start-token/quiescence backend and no Windows Job Object or equivalent dependency. A process group ID plus `kill` result is not by itself the spine's committed boot/start/epoch identity.

**Impact:** Treating process-group creation as complete containment could publish `cancelled` while descendants survive, or signal a recycled identity. Windows implementation could proceed without a viable backend despite the cross-platform wording.

**Smallest fix to the spine:** Keep the invariant, but label the OS-specific identity/quiescence implementation as a technology gate: POSIX and Windows host admission remain disabled until their selected backend passes the exact-identity, child/grandchild, PID-reuse, TERM/KILL, and empty-containment fixtures. Explicitly state that `Bun.spawn({ detached: true })` establishes the POSIX group but does not satisfy the proof by itself.

### LOW-1 — PM2 compatibility is observed, not reproducibly bounded

**Problem:** PM2 is critical to supervisor availability but is neither a repository dependency nor version-gated. The spine correctly labels 6.0.14 as an observation, while new installs currently receive major 7 by default.

**Evidence:** The host runs 6.0.14; npm latest is 7.0.4; the public `--only` contract is documented. No v6-private behavior was identified.

**Impact:** Low at architecture time, but unrecorded PM2 major changes can make a new install differ from the reviewed production host.

**Smallest fix to the spine:** Preserve “observation,” add a tested/supported PM2 major statement or deployment preflight, and record the PM2 version in diagnostics. Do not require a v7 upgrade solely for currency.

## Claims that pass without revision

- The Claude `0.3.209` exact pin and Codex `0.144.5` lockfile claims are correct.
- Being behind the 2026-09-21 npm latest versions is not itself a defect; deterministic conformance is more important than currency for recovery code.
- PM2's documented `--only` behavior is a valid basis for API-only restarts. The current ecosystem-wide restart is expected pre-feature behavior because the current ecosystem has only one app.
- PostgreSQL transactions and `LISTEN`/`NOTIFY` support are already present, while bounded polling remains a valid correctness backstop for both database modes.
- The package layering and web-as-HTTP-client claims match current manifests.
- The spine does not need to commit to PostgreSQL 18 merely because it is the newest stable major; the repository's PostgreSQL 17 test/deployment line is supported. The observed `psql 18.6` is a client tool only.

## Minimum revision set

1. Gate SQLite managed execution on a runtime-observed fixed SQLite version and record Bun + SQLite identities per release.
2. Rewrite the Bun Stack row to separate manifest range, CI/Docker baseline, local observation, and target runtime pin.
3. Label Claude/Codex strict recovery as a new adapter contract, not an existing capability of the general resume path.
4. Label exact POSIX/Windows containment backends as admission-gated until their platform proof fixtures pass.
5. Record a tested PM2 major range or preflight while retaining public `--only` semantics.

After items 1–4, the named technology choices are credible for the architecture. Item 5 is a low-risk hardening clarification.
